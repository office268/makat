# קטלוג מק"טים לחלקי רכב

אפליקציית web בפייתון לניהול וזיהוי מק"טים של חלקי חילוף לרכב.

**הרעיון המרכזי:** תמונה של חלק לא יכולה להחזיר מק"ט מדויק — שתי רפידות בלם עם
מק"טים שונים נראות זהות בצילום. לכן המערכת מפרידה בין שני מקורות מידע ומצליבה ביניהם:

```
מספר רישוי  →  רכב מדויק (יצרן, דגם, שנה, קוד מנוע)   ← מצמצם את מרחב החיפוש
                                  ↓
תמונה / תיאור  →  סוג החלק ("דיסק בלם קדמי")           ← זה מה ש-AI עושה טוב
                                  ↓
                    הצטלבות  →  מק"ט יחיד + מחיר
```

## הרצה מהירה

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export FLASK_APP=app:create_app
flask db upgrade            # יוצר את הסכימה
python scripts/import_parts_csv.py data/parts_catalog.csv   # 2,090 מק"טים
python run.py               # http://127.0.0.1:5000/identify
```

המיגרציה כותבת את המורשים הראשונים, וההזדהות היא מספר הטלפון שלהם —
שדה אחד, בלי סיסמה. מכאן והלאה מוסיפים מספרים מ-`/team`.

במסך הזיהוי אפשר ללחוץ על אחד ממספרי הרישוי לדוגמה, לכתוב "רפידות קדמיות"
או "פילטר שמן", ולקבל את המק"ט המתאים בדיוק לרכב הזה.

`data/gap_parts_seed.csv` הוא זרע ממוקד: 26 מק"טים לשישה דגמים שהיו
ב-**"אין כיסוי"** בראש דירוג הפערים (IONIQ HYBRID, IBIZA, SX4 CROSSOVER,
VITARA, ARONA, KODIAQ). לכל שורה יש מק"ט מקורי ב-`cross_refs` ומקור
ב-`notes`, והוא נטען כמו כל מחירון: `/import` או
`python scripts/import_parts_csv.py data/gap_parts_seed.csv`.

הקטלוג ב-`data/parts_catalog.csv` הוא 2,090 מק"טים אמיתיים של יצרני חלפים, שנאספו
מקטלוג מקוון לא רשמי (AUTODOC). כל שורה נושאת את המקור הזה בשדה `notes`,
ולכן הוא ניתן לאיתור ולהחלפה כשייכנס מקור מורשה. אין במערכת מסלול שמייצר
מק"טים סינתטיים.

### מסך הפתיחה

`/welcome` הוא הדלת: מכונית בקווי מתאר בלבד, שקופה, מסתובבת במרכז
המסך, ולחיצה עליה נכנסת לאפליקציה. המכונית נבנית בקוד
(`static/js/car3d.js`) ומצוירת על canvas דו-ממדי — בלי WebGL ובלי קובץ
מודל. שלוש סיבות: הדף נטען מיד, הוא נשמר במטמון ה-PWA ועובד אופליין,
ואין תלות בספרייה חיצונית שצריך לתחזק. העומק נמסר בשקיפות בלבד: קווים
רחוקים דהויים ודקים, קרובים בהירים וזוהרים.

הכניסה עצמה היא קישור רגיל (`<a href>`) ולא מאזין לחיצה על ה-canvas,
כדי שהיא תעבוד גם ב-Tab, גם בקורא מסך וגם כשה-JavaScript לא נטען.
מי שביקש `prefers-reduced-motion` מקבל את המכונית עומדת, בלי סיבוב
ובלי אנימציית מעבר.

**מתי היא מופיעה.** בכל פתיחה של האפליקציה. `GET` נקי של השורש מגיע
קודם למסך הפתיחה, אלא אם כן הוא נושא אחד משניים: אסימון כניסה
חד-פעמי, שמקבל מי שלחץ על המכונית ונשרף מיד (בלעדיו הייתה נוצרת
לולאה בדפדפן שאינו שולח `Referer`), או מפנה מהאתר עצמו — כלומר
ניווט ממסך אחר, שאינו פתיחה של האפליקציה.

ההבחנה היא בין ניווט לפתיחה, לא בין קרוב לרחוק בזמן. מדידה לפי זמן
נוסתה קודם ונכשלה: מי שסגר ופתח את האפליקציה אחרי דקה פתח אותה מחדש
לכל דבר, גם אם השעון בקושי זז.

מה שאינו נחסם, ובכוונה: `/?plate=...` הוא תוצאה ששיתפו והפניה הייתה
מאדה את מספר הרישוי; `POST /` הוא חיפוש שחייב להגיע ליעד; ושאר
המסכים נפתחים ישירות, כי קישור עמוק שנשלח לעובד צריך להוביל למקום
שאליו הוא מצביע.

**החזרה שאינה מגיעה לשרת.** דפדפן משחזר דף מהזיכרון בלי לפנות
לשרת — PWA שנפתח מחדש, לשונית שחוזרים אליה, כפתור "אחורי". בבקשה
שלא נשלחת אין למה ש-`splash_gate` ייתפס, ולכן הדף מחזיר את עצמו:
`static/js/app.js` מזהה יציאה מהאפליקציה וחזרה אליה, ומגיע לאותה
מסקנה כמו השרת. הסף (חצי דקה — מספיק כדי להבדיל בין מעבר רגעי
לאפליקציה אחרת לבין יציאה אמיתית) והיעד מגיעים אליו כ-`data-splash-away`
ו-`data-splash-url` על ה-`body`, כדי שיהיה מקור אמת אחד. מסך עם תוצאות חיפוש אינו מקבל
אותם — שם המשתמש היה מאבד את מה שכבר על המסך. באותה רוח דלת הכניסה
מוגשת עם `Cache-Control: no-store`, אחרת הדפדפן מגיש אותה מהמטמון
שלו והשער לא רץ.

## ארגונים, משתמשים והרשאות

המערכת בנויה לריבוי לקוחות, בשתי שכבות:

| שכבה | טבלאות | מי רואה |
|---|---|---|
| **קטלוג משותף** | `parts`, `manufacturers`, `categories`, `fitments`, `cross_references` | כולם |
| **שכבה פרטית** | `org_parts` (מחיר, עלות, מלאי, מיקום), `suppliers` | הארגון בלבד |

לקוח חדש מקבל קטלוג מלא ביום הראשון במקום מסך ריק, ובכל זאת המחירים
שלו — המידע המסחרי הרגיש — נשארים שלו. מי שלא הזדהה אינו רואה דבר:
האפליקציה כולה סגורה מאחורי שדה הטלפון.

`Part.for_org(organization_id)` היא נקודת הגישה היחידה לשכבה הפרטית,
וכל מסך, נקודת API וייצוא CSV עוברים דרכה.

| תפקיד | קריאה | עריכת קטלוג | ניהול משתמשים |
|---|---|---|---|
| בעלים (`owner`) | ✅ | ✅ | ✅ |
| מנהל (`manager`) | ✅ | ✅ | ❌ |
| מכונאי (`mechanic`) | ✅ | ❌ | ❌ |

השבתת ארגון מנתקת אוטומטית את כל המשתמשים שלו.

### ההזדהות: מספר טלפון

הלחיצה על המכונית מובילה ל-`/login`, ושם יש שדה אחד — מספר טלפון.
המספר נשמר מנורמל (`app/phones.py`), כך ש-`052-797-7040`, `+972527977040`
ו-`0527977040` הם אותו אדם. אין סיסמה, אין הרשמה עצמית ואין הזמנה
בדוא"ל: **טבלת המשתמשים היא רשימת המורשים**, ומי שאינו בה נעצר בדלת.

זו הסיבה שהרשימה יושבת בבסיס הנתונים ולא במשתנה סביבה: "מי מורשה
להיכנס" הוא נתון שמשתנה, ובעלים מוסיף ומשבית אותו מ-`/team` בלי
פריסה מחדש. משתנה הסביבה נשאר רק ל-`SUPERADMIN_EMAILS`, שצריך להיות
מחוץ להישג ידו של היישום עצמו.

**שער ההזדהות** (`identification_gate` ב-`app/auth.py`) חוסם כל מסך
פרט לדלת עצמה: `/welcome`, `/login`, `/enter`, המניפסט, ה-service
worker ו-`/healthz`. בקשת API שלא הזדהתה מקבלת 401, בקשת דפדפן מופנית
לשדה — עם היעד שאליו כיוונה, כך שקישור עמוק נפתח במקום הנכון אחרי
ההזדהות.

**אבטחה:** CSRF על כל הטפסים, קוקיז `HttpOnly`+`SameSite` ו-`Secure`
בפרודקשן, וכל ניסיון כניסה — מוצלח או לא — נרשם בלוג השימוש עם המספר
והסיבה. `READ_ONLY=1` הוא מתג חירום שחוסם שינוי נתונים גם למשתמש מורשה.

שדה יחיד פירושו שהמספר הוא גם הזהות וגם הסוד: מי שיודע מספר מורשה
נכנס. זה מתאים לצוות סגור ומוכר, ולא לפתיחה לקהל. השלב הבא הטבעי,
כשיידרש, הוא קוד חד-פעמי ב-SMS על אותו שדה עצמו — המסך והמודל כבר
בנויים סביב מספר הטלפון.

## לוג השימוש

`/activity` הוא התיעוד המלא של מה שקורה במערכת: **שורה אחת לכל בקשה
משמעותית**, עם המשתמש, הארגון, הפעולה, הנתיב, קוד הסטטוס ומשך הטיפול
במילישניות. המסך פתוח לבעלים של הארגון (`owner`) ולמנהל מערכת.

| מה יש בו | פירוט |
|---|---|
| כותרות | אירועים, משתמשים פעילים, פעולות שינוי, שגיאות, זמן תגובה ממוצע |
| רצועת שימוש | ספירת אירועים ל-14 הימים האחרונים |
| דירוגים | הפעולות הנפוצות, ומי המשתמשים הפעילים ביותר |
| טבלה | כל אירוע, עם פרטים שאפשר לפתוח בשורה |
| סינון | טווח זמן, חיפוש חופשי, פעולה, משתמש, שינויים בלבד / שגיאות בלבד |
| ייצוא | `/activity.csv` באותם סינונים, ו-`/activity/<id>` כ-JSON |

הכתיבה אוטומטית (`after_request`), ומסכים שיודעים לספר יותר מוסיפים פרטים
דרך `activity.note()` — מספר הרישוי שחופש וכמה תוצאות חזרו, כמה שורות
יובאו מ-CSV, איזה מק"ט נערך, למה ניסיון הזדהות נכשל. הפרטים נספחים
לאותה שורה, כך שיש אירוע אחד לכל פעולה של המשתמש.

**מה לא נכנס ללוג:** ערכי שדות של טפסים. נשמרים רק שמות השדות, ושדות
רגישים (סיסמה, טוקן, `csrf_token`) לא נשמרים אפילו בשם. רעש שאינו מספר
כלום — קבצים סטטיים, `/healthz`, והפולינג של מסכי הניהול — לא נרשם.

**גבולות ארגון:** בעלים רואה רק את מה שקרה בארגון שלו. מנהל מערכת יכול
לעבור לתצוגה חוצת-ארגונים (`?scope=all`), ורק הוא רואה גם את השימוש
האנונימי במסך הזיהוי, שאינו משויך לאף ארגון.

```bash
flask prune-activity   # מוחק אירועים ישנים מ-ACTIVITY_LOG_RETENTION_DAYS
```

## התקנה כאפליקציה

האפליקציה היא PWA וניתנת להתקנה למסך הבית — שימושי למכונאי שעובד
מהטלפון ומצלם חלקים.

- **אנדרואיד / Chrome**: כפתור "📲 התקן" בסרגל הניווט, או תפריט הדפדפן ← "התקן אפליקציה"
- **iPhone / Safari**: שיתוף ← "הוסף למסך הבית"

`app/routes/pwa.py` מגיש את המניפסט ואת ה-service worker **מהשורש** ולא
מ-`/static`, כי היקף ה-service worker מוגבל לנתיב שממנו הוגש.

**מה נשמר במטמון:** נכסים סטטיים בלבד. דפים תמיד נמשכים מהרשת, כי הם
מציגים מחירים, מלאי וזיהוי רכב חי — הגשה מהמטמון הייתה מציגה נתונים
ישנים כאילו הם עדכניים. בלי חיבור מוצג מסך ניתוק מפורש.

האייקונים נוצרים ב-`python scripts/make_icons.py`, וגרסת ה-service
worker נגזרת מה-commit כדי שדפדפנים ימשכו נכסים מחדש בכל פריסה.

## עמודות טבלת המק"טים

הטבלה ב-`/parts` אינה קבועה בקוד. **מנהל האפליקציה** קובע ב-`/admin/columns`
אילו עמודות מוצגות ובאיזה סדר, וההחלטה חלה על כל המשתמשים במערכת —
זו לא העדפה אישית אלא מה שנכון להראות.

| מה אפשר | איך |
|---|---|
| סדר | ▲/▼ לכל עמודה במסך הניהול |
| הוספה והסרה | מרשימת העמודות הזמינות, לצד המוצגות |
| מיון | אייקון שליד הכותרת. לחיצה ממיינת, לחיצה שנייה הופכת את הכיוון, והאייקון עצמו מראה את המצב |
| סינון | אייקון משפך שליד הכותרת, ומתחתיו נפתח השדה — טקסט, מספר או רשימה נפתחת, לפי סוג העמודה |

**מה יש ברשימה:** זהות המק"ט (מספר, מק"ט מקורי, שם, שם באנגלית, ברקוד,
יצרן, קטגוריה, סוג חלק, צד, מידות, משקל, אחריות), השכבה המסחרית של
הארגון (מחיר, עלות, מלאי, מלאי מינימלי, מיקום במחסן), הרכב שהחלק מתאים
לו (מתאים ל, יצרן רכב, דגם רכב), ושתי עמודות שסופרות את הקטלוג עצמו:

| עמודה | מה היא סופרת |
|---|---|
| **חלפים במאגר** | כמה מק"טים בקטלוג מתאימים לרכב של השורה הזאת. אותו מספר בדיוק שמסך `/stats` מציג לדגם, ובאותו כיווץ כתיב (`RAV 4` = `RAV4`). לחלק שמתאים לכמה רכבים — הרכב הרחב מביניהם |
| **תחליפים** | כמה מק"טים אחרים בקטלוג אפשר לשים במקומו: אותו כלל בדיוק כמו רשימת "מק"טים שקולים בקטלוג" שבכרטיס המק"ט |

### חשיבות החלק

שלוש עמודות נוספות עונות על "כמה זה חשוב", מתוך ספירת הצי של משרד
התחבורה — אותם מספרים שמסך `/stats` מציג, ובאותה הצלבה:

| עמודה | מה היא אומרת |
|---|---|
| **רכבים על הכביש** | כמה רכבים כאלה פעילים במרשם |
| **בטווח הקנייה** | מתוכם בני 4–12: מחוץ לאחריות ועדיין נוסעים — חלון האפטרמרקט |
| **רכבים למק"ט** | רכבים בטווח הקנייה על כל מק"ט שכבר יש לדגם. גבוה = פער גדול, כלומר הזדמנות |

לחלק שמתאים לכמה רכבים מוצג **הגדול מביניהם** — הרכב הנפוץ ביותר שהוא
משרת. סכום היה סופר פעמיים דגם שנספר לשני שמות בקטלוג.

**ההצלבה בין המרשם לקטלוג היא לוגיקה של פייתון ולא של SQL:** המרשם כותב
"טויוטה יפן" ו-"COROLLA HSD SDN", הקטלוג "טויוטה" ו-"COROLLA". הנרמול
הזה (שמגשר גם על "מזדה" מול "מאזדה") אינו ניתן לכתיבה ב-SQL בלי לשנות
אותו, ומספר שסותר את מסך הצי גרוע ממספר שחסר.

מה שכן: **הקטלוג כולו מחזיק כמה עשרות צמדי רכב בלבד** (39 בקטלוג
הנוכחי). ההצלבה נעשית בפייתון פעם אחת, והתוצאה — טבלה קטנה — נכתבת
לתוך השאילתה כ-`CASE`, כך שהמיון והסינון רצים בבסיס הנתונים על אותם
מספרים שהתא מציג. נמדד על 2,400 מק"טים מול צילום של 20,000 דגמים:
מיון 40–60 אלפיות, דף שלם 130.

מה שיקר — נרמול עשרות אלפי שורות המרשם — נשמר בזיכרון **לפי חותמת
הצילום**, שהיא זהות הצילום במערכת. צילום חדש פוסל את הזיכרון מאליו,
ולכן אין כאן מטמון שצריך לזכור לנקות.

**בלי ספירת צי טעונה** התאים מציגים "—" ולא 0: "לא ידוע" אינו "אין
רכבים כאלה".

שתי הספירות האלה מקובצות בתת-שאילתה אחת ולא נספרות מחדש לכל שורה.
הניסוח המתבקש — תת-שאילתה שרצה לכל מק"ט — לקח **שבע שניות** למיון לפי
תחליפים על קטלוג של 2,400 מק"טים, כי `lower()` מבטל את האינדקס והחיפוש
הופך לסריקה מלאה. אחרי הקיבוץ: 14 אלפיות. הערך שמוצג בתא מגיע מאותו
ביטוי שלפיו ממיינים, בשאילתה אחת לכל הדף — אחרת המספר בתא היה יכול
לסתור את הסדר שהוא עצמו יצר.

**סינון מספרי** מקבל מספר (`8`), טווח (`10-20`) או השוואה (`>10`, `<=50`).
מה שאי אפשר לקרוא כמספר פשוט לא מסנן — מסנן שהוקלד למחצה לא אמור לרוקן
את הטבלה.

המיון והסינון חיים יחד ונשמרים זה בזה: לחיצה על כותרת לא מאבדת את
הסינון, וסינון לא מחזיר את הטבלה למיון ברירת המחדל.

שני האייקונים יושבים בכותרת עצמה ואין שורת סינון נפרדת. שדה הסינון
נפתח *בתוך* הכותרת (`<details>`) ולא כחלונית צפה מעליה — חלונית הייתה
נחתכת בגלילה האופקית של הטבלה, דווקא בעמודות הקיצוניות. עמודה שכבר
מסוננת נפתחת מעצמה, אחרת הערך שסונן היה נעלם מהעין.

**בזמן שהשרת ממיין ומסנן** מופיע פס בראש הטבלה והנתונים הישנים
מתעמעמים. מיון וסינון אינם קורים בדפדפן אלא בבקשה לשרת, ובין הלחיצה
לבין הדף החדש המסך מציג את התוצאה הקודמת — בדיוק המצב שנראה תקוע.
הפס בלתי-מוגדר בכוונה: אין מה למדוד, ויש מה לומר. אותו חיווי עולה גם
במעבר בין עמודי התוצאות.

`app/part_columns.py` הוא מקור האמת: הכותרת, ביטוי המיון, סוג הסינון
והערך שמוצג בתא יושבים שם יחד, כך שעמודה חדשה היא רשומה אחת ולא סיור
בין תבנית, מסלול ושאילתה. הפריסה עצמה — הסדר ומה מוצג — נשמרת ב-DB
(`table_layouts`), ולכן שינוי שלה אינו דורש פריסה מחדש. אין שורה שמורה =
ברירת המחדל שבקוד, ולכן הטבלה עובדת ביום הראשון.

**מיון לפי מחיר הולך אחרי מה שכתוב בעמודה:** העמודה מציגה מחיר כולל
מע"מ, ולכן גם המיון והסינון מחשבים אותו — ולא את המחיר הגולמי, שיכול
לתת סדר אחר כשחלק מהשורות כבר כוללות מע"מ.

## גודל התצוגה

בתפריט הניווט — זה שמתקפל מאחורי ההמבורגר בטלפון — יש סעיף **הגדרות**
עם שני זוגות כפתורים, ‎+‎ ו-‎−‎:

| | מה זה משנה |
|---|---|
| **זום** | את הדף כולו, כמו הזום של הדפדפן: טקסט, כפתורים, מסגרות ותמונות גדלים יחד והפריסה נשארת כשהייתה |
| **גודל טקסט** | את גודל הבסיס שכל הטיפוגרפיה נמדדת ממנו: הטקסט והמרווחים שסביבו גדלים, התמונות לא, והשורות נשברות מחדש |

במוסך צריך את שניהם: זום כשמסתכלים על המסך ממרחק זרוע, גודל טקסט
כשרוצים יותר מק"טים על אותו מסך בלי לוותר על קריאוּת.

הטווח הוא 50%–180% לזום ו-80%–180% לטקסט, **בצעדים של 5%**. כפתור שהגיע
לקצה מושבת, ו"איפוס לגודל רגיל" מחזיר את שניהם ל-100%. הזום יורד עד חצי
כי שם נכנסת טבלת מק"טים שלמה למסך אחד.

**הגדלת טקסט מכווצת את הריפוד.** ריפוד נמדד ב-rem ולכן הוא גדל עם הגופן
מעצמו — והגדלה הייתה מוסיפה בעיקר רווח לבן ודוחקת שורות אל מחוץ למסך.
במקום זה הוא מתכווץ: ב-140% טקסט הריפוד הוא 80% מגודלו הרגיל, וב-180%
הוא 60%. כך ההגדלה מוסיפה אותיות, לא אוויר. הכיווץ חל על תאי הטבלאות,
על הכרטיסים, על רשימות ה-`list-group` ועל העטיפה של תוכן העמוד.

**ההגדרה שייכת למכשיר ולא לחשבון** (`localStorage`) — אותו אדם רוצה
גודל אחד על מסך המשרד ואחר על הטלפון, ולכן היא לא נשמרת בשרת.
`static/js/display.js` נטען ב-`<head>` ולא בסוף הדף: הוא מחיל את מה
שנשמר לפני הציור הראשון, אחרת הדף היה נפתח בגודל רגיל וקופץ לגודלו.
בגלישה פרטית שבה האחסון חסום המסך עדיין משתנה, פשוט לא נזכר.

## הוספת עובדים

בעלים מוסיף מספר טלפון מ-`/team`, קובע לו תפקיד, ומאותו רגע אפשר
להיכנס איתו — אין הזמנה לשלוח ואין סיסמה לקבוע. מי שעזב מושבת באותו
מסך, וההשבתה שוללת את הכניסה מיד. אי אפשר להוריד בדרגה או להשבית את
הבעלים האחרון — ארגון לא יכול לנעול את עצמו החוצה.

## איתור רכב לפי מספר רישוי

`app/vehicles.py` פונה למאגר כלי הרכב הפתוח של משרד התחבורה
(`data.gov.il`) — חינמי ולא דורש מפתח. אם אין גישה לרשת, המודול נופל
אוטומטית לקובץ `data/vehicles_sample.json` עם עשרה רכבי דוגמה, כך שהזיהוי
ממשיך לעבוד. זו נפילה של *חיפוש הרכב* בלבד — המק"טים מגיעים מהקטלוג בכל
מקרה. מקור הנתונים מוצג במסך (`data.gov.il` מול `offline`), והמסך אומר
במפורש כשפרטי הרכב הגיעו מהקובץ המקומי.

## קטלוג דגמי הרכב

התאמת מק"ט לרכב היא מה שמפעיל את החיפוש לפי מספר רישוי, ולכן היצרן והדגם
חייבים לבוא מרשימה סגורה: כשהם טקסט חופשי, "טויוטה" ו-"טויוטה יפן" הם שני
ערכים שונים וההצטלבות נכשלת. המקור הוא מאגר "תוצרים ודגמים" הפתוח של משרד
התחבורה — מעל 100 אלף רשומות, שורה לכל שנת ייצור, מכווצות לדגמים עם טווחי שנים.

שתי דרכים לייבא, שתיהן חולקות את `app/vehicle_import.py`:

```bash
python scripts/import_vehicle_models.py            # מהשורה, לפיתוח מקומי
python scripts/import_vehicle_models.py --file x.json   # מקובץ שכבר הורד
```

בפרודקשן דרך היישום: מסך `/admin/vehicle-import`, פתוח למי שכתובתו ב-
`SUPERADMIN_EMAILS`. הייבוא רץ **במנות** — כל בקשה מייבאת כמה עמודים ומקדמת
את נקודת ההמשך, כי משיכה של הכל בבקשה אחת חורגת מה-timeout של gunicorn.
ההתקדמות נשמרת בטבלה `vehicle_import_jobs` ולא בזיכרון, ולכן היא נראית לכל
ה-workers, שורדת נפילה או פריסה מחדש, וניתן להמשיך אותה מהנקודה שנעצרה.

## כמה רכבים מכל דגם על הכביש

`/stats` מציג את הפילוח: כמה רכבים פעילים יש מכל דגם בישראל, מהנפוץ לנדיר,
עם הנתח מכלל הצי, כמה מק"טים מהקטלוג מתאימים לדגם וכמה מהם **מתכלים**
(רפידות, דיסקים, מסננים, רצועות, מצתים ומגבים — `taxonomy.WEAR_TYPES`),
וקישור ישיר לחיפוש החלפים לאותו דגם. עמודות הספירה נשענות על אותו
`search_parts` שהחיפוש מריץ, כדי שהמספר בעמודה יהיה בדיוק מה שנפתח בלחיצה
עליו — הן נבנות ממפת התאמות אחת (`services.part_counts_for`) ולא משאילתה
לכל דגם, ולכן הן זולות גם למאות שורות. הן אינן בייצוא ה-CSV.

### לא כל רכב על הכביש הוא קונה

**חלון האפטרמרקט** הוא בערך 4–12 שנים: רכב חדש עדיין באחריות ובטיפולי
סוכנות, ורכב ישן מאוד כבר בקושי מטופל. הצילום שומר לכל דגם שלושה מונים
(`young`, `prime`, `old`) ולא רק את הסכום, והמסך מציג את **בטווח הקנייה**
לצד סך הרכבים. דגם עם 90 אלף רכבים שכולם מ-2024 אינו שוק; אותם 90 אלף
מ-2016 הם כן. סכום שלושת הדליים יכול להיות קטן מסך הרכבים — רשומה בלי
שנת ייצור אינה בשום דלי.

**רכבים למק"ט** הוא היחס שהופך את הטבלה לרשימת פעולה: כמה רכבים בטווח
הקנייה יש על כל מק"ט שבידינו. ערך גבוה = שוק גדול שאיננו מכסים. דגם בלי
מק"טים כלל מסומן "אין כיסוי" ולא באפס — אין מכנה, וזה הפער המרבי ולא
היעדר פער.

**מיון "הפער הגדול ביותר"** (`?sort=gap`) מדרג את `FLEET_GAP_MODELS`
הדגמים הגדולים בטווח הקנייה לפי `prime ÷ (מק"טים+1)`. הדירוג מוגבל
לדגמים הגדולים בכוונה: פער אצל דגם עם שלושים רכבים אינו הזדמנות, והוא
היה מציף את הרשימה. המקור הוא מרשם כלי
הרכב של משרד התחבורה — אותו מאגר שהזיהוי לפי מספר רישוי עובד מולו, שורה
לכל רכב פעיל, כשלושה מיליון שורות.

הקטלוג יודע אילו דגמים קיימים, לא כמה מהם על הכביש; דגם עם 90 אלף רכבים
ודגם עם 300 נראים אותו דבר ברשימת הדגמים, והם לא אותו דבר כשמחליטים איזה
מק"ט להחזיק במלאי.

הספירה נעשית בצד המאגר — `GROUP BY` אחד דרך נקודת ה-SQL של CKAN — ונשמרת
כצילום מצב בטבלה `fleet_model_counts`. המסך קורא מהטבלה ולא מהמאגר: ספירה
של שלושה מיליון רשומות אינה דבר שמחכים לו בתוך בקשת דפדפן.

**הצילום מוחלף רק כשהוא שלם.** ספירה חדשה נבנית לצד הישנה: כל שורה נושאת את
חותמת ההרצה שכתבה אותה, `/stats` ממשיך להציג את הצילום השלם האחרון, וההחלפה
היא רגע אחד בסוף. חצי ספירה שמוצגת כאילו היא הצי כולו אינה מספר חלקי אלא
מספר שקרי — ולכן גם הרצה שנעצרה או נכשלה נשארת מחוץ לתמונה עד שתושלם.

שתי דרכים להריץ, שתיהן חולקות את `app/fleet_stats.py`:

**מהיישום** — מסך `/admin/fleet-stats`, פתוח למי שכתובתו ב-`SUPERADMIN_EMAILS`.
זו הדרך בפרודקשן, שבה אין טרמינל. הספירה רצה **במנות**, כמו ייבוא קטלוג
הדגמים: כל בקשה מושכת עמוד ומקדמת את נקודת ההמשך, שנשמרת ב-`fleet_stats_jobs`
ולא בזיכרון — ולכן היא נראית לכל ה-workers, שורדת פריסה מחדש וניתן להמשיך
אותה מהנקודה שנעצרה.

**שני מסלולים, החלפה אוטומטית.** נקודת ה-SQL של המאגר אינה זמינה בכל
סביבה — היא מחזירה 404 — ולכן ההרצה מזהה זאת בעצמה ועוברת לסריקה מלאה:
מושכת את שורות הרכב עצמן (32 אלף לבקשה, ארבעה שדות בלבד, `sort=_id` כדי
שהעימוד יהיה יציב) וסופרת כאן. אותה תוצאה בדיוק, לוקח יותר זמן. מצב הספירה
נצבר על ההרצה עצמה בשדה דחוס ולא כשורות ביניים בטבלה, ורק בסוף הוא הופך
לשורות. בסריקה יש סה"כ אמיתי מהמאגר ולכן גם אחוז התקדמות אמיתי; בספירה
אצל המאגר אין למה להשוות, ושם המסך מראה מונים במקום אחוז מומצא.

**משורת הפקודה** — לפיתוח מקומי ולטעינה מקובץ:

```bash
python scripts/vehicle_stats.py --load          # ספירה, CSV וטעינה למסד
python scripts/vehicle_stats.py --min-count 100 # רק דגמים עם 100 רכבים ומעלה
python scripts/vehicle_stats.py --scan --load   # כשנקודת ה-SQL של המאגר סגורה
python scripts/vehicle_stats.py --file rechev.csv  # מקובץ המאגר שהורד ידנית
```

שלושת המסלולים מייצרים את אותן שורות בדיוק. `--scan` מדפדף במאגר בעמודים
של אלף וסופר מקומית — אותה תוצאה, הרבה יותר לאט, ולכן הוא מסלול חירום
ולא ברירת מחדל. הפילוח יורד גם כ-CSV מהמסך עצמו (`/stats.csv`), באותו
סינון שמוצג.

## כשהמרשם והקטלוג קוראים לאותו רכב בשני שמות

שני הצדדים לא מסכימים על שמות, ובכל פעם שההשוואה נכשלת נוצר "אין
כיסוי" מדומה — בדוח, וגרוע מכך גם בזיהוי לפי מספר רישוי:

- **שם הדגם.** לפעמים שם הקטלוג ארוך יותר (`COROLLA VERSO` מול
  `COROLLA`), ולפעמים דווקא שם המרשם (`COROLLA HSD SDN`). לכן ההתאמה
  היא בשני הכיוונים: או ששם המרשם מוכל בשם הקטלוג, או שהוא **מתחיל**
  בו. ההכלה ההפוכה מוגבלת לתחילת המחרוזת ולשמות מאורך `MIN_MODEL_PREFIX`
  ומעלה, אחרת `"3"` היה נדבק גם ל-`I30` וגם ל-`MAZDA 3`.
- **שם היצרן.** המרשם כותב "מזדה" והקטלוג "מאזדה" — אותו יצרן, אֵם
  קריאה אחת הבדל. `normalize_make` מפילה א' ואותיות כפולות ומשווה את
  מה שנשאר. על שנים-עשר היצרנים שבקטלוג היא אינה ממזגת שניים לאחד,
  ולכן היא מגשרת על כתיב בלי להמציא התאמות.

בדירוג הפערים השורות מקובצות לדגם אחד (`grouped_by_model`): לאותו דגם
יש כמה קודי דגם, ולפעמים גם כמה כתיבי יצרן ("מזדה יפן" ו-"מזדה
תאילנד"), ולקטלוג אין הבחנה ביניהם — הם היו מופיעים כשורות נפרדות עם
אותו מספר בדיוק.

## המנוע: מסומן, לא מסונן

חלף מתאים למנוע ולא לשם מסחרי, ולכן ההצטלבות מנסה לזהות גם אותו. אבל
נתוני המנוע בשני הצדדים לא מסתדרים בקלות:

- בקטלוג רק כחמישית מההתאמות מציינות מנוע בכלל, ומי שכן מציין כותב
  בשני כתיבים — רובו נפח ורמת מנוע (`1.4 TSI`), ומיעוטו קוד יצרן
  (`2ZR-FAE`).
- המרשם מוסר קוד יצרן בלבד (`degem_manoa`). הנפח מגיע מקטלוג הדגמים
  שלנו לפי (יצרן, קוד דגם), ומתורגם לכתיב של הקטלוג: 1398 סמ"ק → `1.4`.

`vehicle_engine_terms` מחזיר את שני המונחים, כי כל אחד מהם מוצא חלק אחר
של הקטלוג, וההשוואה מכווצת (`2ZR-FAE` = `2ZRFAE`).

**ומה שנעשה עם זה הוא סימון ולא סינון.** סינון לפי מנוע היה מסתיר מק"ט
נכון שנכתב בכתיב האחר, או כזה שלא ציין מנוע כלל — הפסד גרוע בהרבה
מרשימה קצת ארוכה. לכן כל המק"טים נשארים, אלה שההתאמה שלהם מצהירה על
המנוע של הרכב עולים לראש ומסומנים "מנוע תואם", והשאר ממשיכים להופיע
אחריהם.

הסינון המפורש (`/parts?engine=`) כן מצמצם — אבל גם הוא מכבד את ההבחנה
בין "מנוע אחר" לבין "לא צוין מנוע": התאמה שלא אמרה כלום על מנוע נשארת,
כי היעדר מידע אינו הצהרה שהחלק לא מתאים. קודם לכן היא נמחקה, ואיתה רוב
הקטלוג.

## הגילוי מכוון לפי הפער, לא לפי ניחוש

`/admin/discovery` מחפש מק"טים באינטרנט לפי (יצרן, דגם, סוג חלק). כשלא
מוקלד דגם, המטרות נבחרות **מדירוג הפערים** — כמה רכבים בטווח הקנייה יש
לדגם, חלקי המק"טים שכבר יש לנו עבורו (`fleet_stats.gap_ranking`, אותו
חישוב בדיוק שמאחורי `?sort=gap` במסך).

קודם לכן הן נבחרו לפי מספר הווריאנטים בקטלוג הדגמים — "הפרוקסי היחיד
לפופולריות שיש", כלשון ההערה שהייתה בקוד. מאז נוספה ספירה אמיתית של
מיליוני רכבים, ולכן הגילוי רץ היום על השוק הגדול שאינו מכוסה במקום על
דגם שבמקרה יש לו הרבה קודי דגם. לחפש מק"טים לדגם עם מאתיים מק"טים
קיימים זה בזבוז; לדגם עם חמישים אלף רכבים ואפס מק"טים זו העבודה.

הזוגות מוחזרים בכתיב הקטלוג (`services.catalog_make`), כדי שהתאמות
חדשות יישבו לצד הקיימות ולא יפתחו כתיב שני לאותו יצרן. בלי צילום צי
המסך נופל לפרוקסי הישן — גילוי שמכוון פחות טוב עדיף על מסך שלא עושה
כלום — והוא אומר במפורש לפי מה נבחרו המטרות.

## גריד Autodoc: אותה צנרת, מקור אחר

`/admin/autodoc` מביא חלפים מאתר Autodoc באמצעות **Scrapy**. מנהל
האפליקציה בוחר יצרן, דגם וסוגי חלקים — בדיוק כמו במסך הגילוי — ולוחץ
"התחל גרידה". מטרה אחת (דגם × סוג חלק) בכל בקשת HTTP, כי גרידה של
עמוד לוקחת שניות ו-gunicorn הורג בקשה אחרי 60.

**למה תת-תהליך ולא ייבוא.** Scrapy רץ על Twisted, ו-reactor שנסגר אינו
נפתח שוב באותו תהליך: worker שהריץ גריד אחד היה נשבר בהרצה השנייה.
`app/autodoc.py` מפעיל `scrapy crawl autodoc` כתת-תהליך שכותב JSON
לקובץ זמני, עם תקרת זמן משלו. תת-תהליך שנתקע נהרג לפני שהבקשה נהרגת.

**למה אותו אימות של הגילוי.** מקור אחר, סכנה זהה: עמוד קטגוריה של דגם
מציג גם חלפים שאינם שלו — מסנן של CHERY בעמוד של קורולה, מספר OE של
מרצדס בעמוד של אוקטביה. כל שורה שהגריד מחזיר עוברת ב-`validate` של
`parts_discovery`, כולל השומר שפוסל אזכור של יצרן רכב אחר, ונשמרת דרך
אותו `save`. לכן שתי השיטות חולקות טבלת הרצות אחת (`discovery_jobs`,
עמודת `source`) ומסך סקירה אחד — `/admin/discovery/review` מציג את
שתיהן, עם עמודה שאומרת מאיפה כל מק"ט הגיע.

**מה שהאתר משנה, מתקנים בלי פריסה.** מבנה הכתובות של חנות מקוונת
משתנה, וכתובת שגויה מחזירה אפס תוצאות. שלוש דרכי תיקון, לפי סדר
המאמץ: `AUTODOC_CATEGORIES` (JSON שדורס את מיפוי הקטגוריות),
`AUTODOC_URL_TEMPLATE` (תבנית הכתובת), ואם צריך גם `AUTODOC_SELECTORS`
לעמוד שאין בו JSON-LD. לבדיקה ידנית של כתובת אחת:

```bash
cd scraper
scrapy crawl autodoc -a make=טויוטה -a model=COROLLA \
    -a part_type=oil_filter -O parts.json
scrapy crawl autodoc -a url='https://www.autodoc.co.il/...' \
    -a make=טויוטה -a model=COROLLA -a part_type=oil_filter -O parts.json
```

**הפירוק נבדק מול קובץ, לא מול הרשת.** `scraper/autodoc_scraper/parsers.py`
הוא פונקציות טהורות: HTML נכנס, שורות יוצאות. שני מסלולים לפי סדר
אמינות — JSON-LD שהאתר פולט למנועי חיפוש, ובנפילה סלקטורים על ה-HTML.
`tests/fixtures/autodoc_*.html` הם עמודים שמורים, וכל בדיקות הגריד רצות
בלי לצאת לאינטרנט.

**מנומס כברירת מחדל.** בקשה אחת בכל פעם, שנייה וחצי המתנה ביניהן,
AutoThrottle, וכיבוד `robots.txt`. הכיבוי (`AUTODOC_OBEY_ROBOTS=0`) קיים
למי שיש לו הסכם מול האתר — זו החלטה של מי שמפעיל, ולא ברירת מחדל
שנופלת עליו בשקט. מחיר נגרד ומוצג ביומן אך אינו נשמר בקטלוג: המחיר
בקטלוג הוא שכבה פרטית של ארגון, ומחיר של חנות מקוונת אינו המחיר של המוסך.

## פריסה ל-Railway

### למה זה לא סתם "לחבר ריפו"

SQLite על הדיסק הרגיל של Railway **נמחק בכל deploy** — כל דיפלוי בונה קונטיינר
חדש עם מערכת קבצים נקייה. לכן פרודקשן דורש Postgres (מומלץ) או ווליום קבוע.

### שלבים

1. **צור פרויקט** ב-Railway וחבר אליו את הריפו הזה.
2. **הוסף שירות Postgres** לאותו פרויקט (`+ New → Database → PostgreSQL`).
   Railway מזריק `DATABASE_URL` אוטומטית, והאפליקציה מתרגמת אותו לבד
   לסכמה ש-SQLAlchemy 2 דורש (`postgresql+psycopg://`).
3. **הגדר `SECRET_KEY`** במשתני הסביבה של השירות:
   ```bash
   python -c "import secrets; print(secrets.token_hex(32))"
   ```
   האפליקציה **מסרבת לעלות** על Railway בלי ערך אמיתי — `SECRET_KEY` חותם את
   קוקי הסשן, וערך ברירת המחדל גלוי לכל מי שרואה את הריפו.
4. **לטעינת הקטלוג:** הגדר `IMPORT_PARTS_CSV=data/parts_catalog.csv`. הטעינה
   בטוחה להרצה חוזרת — מק"ט קיים מתעדכן ולא משוכפל.
5. **Generate Domain** בהגדרות השירות — וזהו.

### מה קורה בכל דיפלוי

```
preDeployCommand:  python scripts/init_db.py     ← יוצר טבלאות חסרות, זורע אם ריק
startCommand:      gunicorn --config gunicorn.conf.py "app:create_app()"
healthcheckPath:   /healthz                      ← בודק גם חיבור לבסיס הנתונים
```

`init_db.py` רץ **פעם אחת** לפני שה-workers עולים, ולכן שני workers לא
מתנגשים ביצירת הטבלאות. הוא בטוח להרצה חוזרת.

> **אל תוסיף שורת `release:` ל-`Procfile`.**
> Nixpacks הופך אותה ל**שלב בנייה** בתוך ה-Dockerfile, ו-Railway לא מזריק את
> משתני השירות לבנייה — כך שכל פקודה שם תרוץ בלי `DATABASE_URL` ובלי
> `SECRET_KEY` ותפיל את הבילד. הכנת בסיס הנתונים שייכת ל-`preDeployCommand`
> ב-`railway.json`, שרץ בזמן פריסה עם כל המשתנים.

### חלופה בלי Postgres

מצרפים Volume, ממפים ל-`/data`, ומגדירים `DATA_DIR=/data`. פשוט יותר,
אבל מוגבל למכונה אחת — בלי scaling אופקי.

### משתני סביבה

| משתנה | חובה | תפקיד |
|---|---|---|
| `SECRET_KEY` | ✅ בפרודקשן | חתימת קוקי הסשן |
| `DATABASE_URL` | מוזרק ע"י Railway | חיבור ל-Postgres |
| `DATA_DIR` | חלופה | נתיב לווליום עבור SQLite |
| `SUPERADMIN_EMAILS` | לגישת ניהול | כתובות בעלות הרשאת-על, מופרדות בפסיק |
| `IMPORT_PARTS_CSV` | לא | נתיב CSV לטעינת הקטלוג בכל דיפלוי |
| `ANTHROPIC_API_KEY` | לא | מפעיל זיהוי חלק מתמונה |
| `AUTODOC_CATEGORIES` | לא | מיפוי סוג חלק ← קטגוריה בכתובת, לתיקון בלי פריסה |
| `AUTODOC_OBEY_ROBOTS` | לא | `0` מכבה את כיבוד `robots.txt` בגריד |
| `AUTODOC_TIMEOUT` | לא | תקרת שניות לתת-תהליך הגריד (ברירת מחדל 40) |
| `WEB_CONCURRENCY` | לא | מספר workers (ברירת מחדל 2) |
| `ACTIVITY_LOG_ENABLED` | לא | `0` מכבה את כתיבת לוג השימוש |
| `ACTIVITY_LOG_RETENTION_DAYS` | לא | כמה ימים לשמור אירועים (ברירת מחדל 90) |
| `DISPLAY_TIMEZONE` | לא | אזור הזמן להצגה (ברירת מחדל `Asia/Jerusalem`) |

הרשימה המלאה ב-`.env.example`.

## בדיקות

```bash
python -m pytest tests/ -q
```

מכסות את זיהוי החלקים, איתור הרכב, הצלבת רכב×סוג-חלק, חיפוש לפי מק"ט מקביל,
מחזור ייבוא/ייצוא CSV וחישובי מע"מ ורווחיות.

**ומול Postgres.** ברירת המחדל היא SQLite בזיכרון — מהיר ובלי שרת — אבל
פרודקשן רץ על Postgres, ו-SQLite סלחן במקומות שהוא אינו. שאילתה שעברה
כאן ונפלה שם כבר קרתה, ולכן אותה חבילת בדיקות יודעת לרוץ על שניהם:

```bash
createdb makat_test
TEST_DATABASE_URL=postgresql+psycopg://postgres@127.0.0.1:5432/makat_test \
    python -m pytest tests/ -q
```

שני הבדלים שכבר תפסנו כך, ושתי בדיקות שומרות עליהם גם בלי שרת Postgres:

- **`GROUP BY` מושווה לפי טקסט.** ביטוי שהרווח והמקף שלו נשלחים
  כפרמטרים מקבל מספרים שונים ב-SELECT וב-GROUP BY (`$1` מול `$9`),
  ו-Postgres טוען שהעמודה אינה מקובצת. הערכים נכתבים היום לתוך ה-SQL.
- **NULL ממוין ראשון ב-SQLite ואחרון ב-Postgres.** ספירה של מק"ט בלי
  התאמות מחזירה NULL, והתא מציג 0 — כך שאותה לחיצה על כותרת הייתה
  נותנת שתי תשובות שונות. הספירות עטופות ב-`coalesce`.
