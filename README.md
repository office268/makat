# קטלוג מק"טים לחלקי רכב

אפליקציית web בפייתון לניהול וזיהוי מק"טים של חלקי חילוף לרכב.

**הרעיון המרכזי:** תמונה של חלק לא יכולה להחזיר מק"ט מדויק — שתי רפידות בלם עם
מק"טים שונים נראות זהות בצילום. לכן המערכת מפרידה בין שני מקורות מידע ומצליבה ביניהם:

```
מספר רישוי  →  רכב מדויק (יצרן, דגם, שנה, קוד מנוע)   ← מצמצם את מרחב החיפוש
                                  ↓
תמונה / תיאור  →  סוג החלק ("דיסק בלם קדמי")           ← זה מה ש-AI עושה טוב
                                  ↓
                    הצטלבות  →  מק"ט יחיד + מחיר
```

## הרצה מהירה

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export FLASK_APP=app:create_app
flask db upgrade            # יוצר את הסכימה
python scripts/import_parts_csv.py data/parts_catalog.csv   # 2,090 מק"טים
python run.py               # http://127.0.0.1:5000/identify
```

המיגרציה כותבת את המורשים הראשונים, וההזדהות היא מספר הטלפון שלהם —
שדה אחד, בלי סיסמה. מכאן והלאה מוסיפים מספרים מ-`/team`.

במסך הזיהוי אפשר ללחוץ על אחד ממספרי הרישוי לדוגמה, לכתוב "רפידות קדמיות"
או "פילטר שמן", ולקבל את המק"ט המתאים בדיוק לרכב הזה.

`data/gap_parts_seed.csv` הוא זרע ממוקד: 26 מק"טים לשישה דגמים שהיו
ב-**"אין כיסוי"** בראש דירוג הפערים (IONIQ HYBRID, IBIZA, SX4 CROSSOVER,
VITARA, ARONA, KODIAQ). לכל שורה יש מק"ט מקורי ב-`cross_refs` ומקור
ב-`notes`, והוא נטען כמו כל מחירון: `/import` או
`python scripts/import_parts_csv.py data/gap_parts_seed.csv`.

הקטלוג ב-`data/parts_catalog.csv` הוא 2,090 מק"טים אמיתיים של יצרני חלפים, שנאספו
מקטלוג מקוון לא רשמי (AUTODOC). כל שורה נושאת את המקור הזה בשדה `notes`,
ולכן הוא ניתן לאיתור ולהחלפה כשייכנס מקור מורשה. אין במערכת מסלול שמייצר
מק"טים סינתטיים.

| `/login` | ההזדהות: שדה אחד, מספר טלפון |

| `/parts/<id>` | כרטיס מק"ט: מחירים, מלאי, מק"טים מקבילים, התאמות, ספקים |

### מסך הפתיחה

`/welcome` הוא הדלת: מכונית בקווי מתאר בלבד, שקופה, מסתובבת במרכז
המסך, ולחיצה עליה נכנסת לאפליקציה. המכונית נבנית בקוד
(`static/js/car3d.js`) ומצוירת על canvas דו-ממדי — בלי WebGL ובלי קובץ
מודל. שלוש סיבות: הדף נטען מיד, הוא נשמר במטמון ה-PWA ועובד אופליין,
ואין תלות בספרייה חיצונית שצריך לתחזק. העומק נמסר בשקיפות בלבד: קווים
רחוקים דהויים ודקים, קרובים בהירים וזוהרים.

הכניסה עצמה היא קישור רגיל (`<a href>`) ולא מאזין לחיצה על ה-canvas,
כדי שהיא תעבוד גם ב-Tab, גם בקורא מסך וגם כשה-JavaScript לא נטען.
מי שביקש `prefers-reduced-motion` מקבל את המכונית עומדת, בלי סיבוב
ובלי אנימציית מעבר.

**מתי היא מופיעה.** בכל פתיחה של האפליקציה. `GET` נקי של השורש מגיע
קודם למסך הפתיחה, אלא אם כן הוא נושא אחד משניים: אסימון כניסה
חד-פעמי, שמקבל מי שלחץ על המכונית ונשרף מיד (בלעדיו הייתה נוצרת
לולאה בדפדפן שאינו שולח `Referer`), או מפנה מהאתר עצמו — כלומר
ניווט ממסך אחר, שאינו פתיחה של האפליקציה.

ההבחנה היא בין ניווט לפתיחה, לא בין קרוב לרחוק בזמן. מדידה לפי זמן
נוסתה קודם ונכשלה: מי שסגר ופתח את האפליקציה אחרי דקה פתח אותה מחדש
לכל דבר, גם אם השעון בקושי זז.

מה שאינו נחסם, ובכוונה: `/?plate=...` הוא תוצאה ששיתפו והפניה הייתה
מאדה את מספר הרישוי; `POST /` הוא חיפוש שחייב להגיע ליעד; ושאר
המסכים נפתחים ישירות, כי קישור עמוק שנשלח לעובד צריך להוביל למקום
שאליו הוא מצביע.

**החזרה שאינה מגיעה לשרת.** דפדפן משחזר דף מהזיכרון בלי לפנות
לשרת — PWA שנפתח מחדש, לשונית שחוזרים אליה, כפתור "אחורי". בבקשה
שלא נשלחת אין למה ש-`splash_gate` ייתפס, ולכן הדף מחזיר את עצמו:
`static/js/app.js` מזהה יציאה מהאפליקציה וחזרה אליה, ומגיע לאותה
מסקנה כמו השרת. הסף (חצי דקה — מספיק כדי להבדיל בין מעבר רגעי
לאפליקציה אחרת לבין יציאה אמיתית) והיעד מגיעים אליו כ-`data-splash-away`
ו-`data-splash-url` על ה-`body`, כדי שיהיה מקור אמת אחד. מסך עם תוצאות חיפוש אינו מקבל
אותם — שם המשתמש היה מאבד את מה שכבר על המסך. באותה רוח דלת הכניסה
מוגשת עם `Cache-Control: no-store`, אחרת הדפדפן מגיש אותה מהמטמון
שלו והשער לא רץ.

## ארגונים, משתמשים והרשאות

המערכת בנויה לריבוי לקוחות, בשתי שכבות:

| שכבה | טבלאות | מי רואה |
|---|---|---|
| **קטלוג משותף** | `parts`, `manufacturers`, `categories`, `fitments`, `cross_references` | כולם |
| **שכבה פרטית** | `org_parts` (מחיר, עלות, מלאי, מיקום), `suppliers` | הארגון בלבד |

לקוח חדש מקבל קטלוג מלא ביום הראשון במקום מסך ריק, ובכל זאת המחירים
שלו — המידע המסחרי הרגיש — נשארים שלו. מי שלא הזדהה אינו רואה דבר:
האפליקציה כולה סגורה מאחורי שדה הטלפון.

`Part.for_org(organization_id)` היא נקודת הגישה היחידה לשכבה הפרטית,
וכל מסך, נקודת API וייצוא CSV עוברים דרכה.

| תפקיד | קריאה | עריכת קטלוג | ניהול משתמשים |
|---|---|---|---|
| בעלים (`owner`) | ✅ | ✅ | ✅ |
| מנהל (`manager`) | ✅ | ✅ | ❌ |
| מכונאי (`mechanic`) | ✅ | ❌ | ❌ |

השבתת ארגון מנתקת אוטומטית את כל המשתמשים שלו.

### ההזדהות: מספר טלפון

הלחיצה על המכונית מובילה ל-`/login`, ושם יש שדה אחד — מספר טלפון.
המספר נשמר מנורמל (`app/phones.py`), כך ש-`052-797-7040`, `+972527977040`
ו-`0527977040` הם אותו אדם. אין סיסמה, אין הרשמה עצמית ואין הזמנה
בדוא"ל: **טבלת המשתמשים היא רשימת המורשים**, ומי שאינו בה נעצר בדלת.

זו הסיבה שהרשימה יושבת בבסיס הנתונים ולא במשתנה סביבה: "מי מורשה
להיכנס" הוא נתון שמשתנה, ובעלים מוסיף ומשבית אותו מ-`/team` בלי
פריסה מחדש. משתנה הסביבה נשאר רק ל-`SUPERADMIN_EMAILS`, שצריך להיות
מחוץ להישג ידו של היישום עצמו.

**שער ההזדהות** (`identification_gate` ב-`app/auth.py`) חוסם כל מסך
פרט לדלת עצמה: `/welcome`, `/login`, `/enter`, המניפסט, ה-service
worker ו-`/healthz`. בקשת API שלא הזדהתה מקבלת 401, בקשת דפדפן מופנית
לשדה — עם היעד שאליו כיוונה, כך שקישור עמוק נפתח במקום הנכון אחרי
ההזדהות.

**אבטחה:** CSRF על כל הטפסים, קוקיז `HttpOnly`+`SameSite` ו-`Secure`
בפרודקשן, וכל ניסיון כניסה — מוצלח או לא — נרשם בלוג השימוש עם המספר
והסיבה. `READ_ONLY=1` הוא מתג חירום שחוסם שינוי נתונים גם למשתמש
מורשה; **כבוי כברירת מחדל**, כי ההגנה היומיומית היא ההרשאות.

ה-API פטור מאסימון ה-CSRF — לקוח שאינו דפדפן אינו יכול לקבל אחד.
מה שמגן עליו הוא `SameSite=Lax`: דפדפן אינו שולח את קוקי הסשן בבקשת
כתיבה שיצאה מאתר אחר. **אין מפתחות API במערכת** — ההזדהות שם היא
אותו קוקי בדיוק כמו במסכים.

שדה יחיד פירושו שהמספר הוא גם הזהות וגם הסוד: מי שיודע מספר מורשה
נכנס. זה מתאים לצוות סגור ומוכר, ולא לפתיחה לקהל. השלב הבא הטבעי,
כשיידרש, הוא קוד חד-פעמי ב-SMS על אותו שדה עצמו — המסך והמודל כבר
בנויים סביב מספר הטלפון.

## לוג השימוש

`/activity` הוא התיעוד המלא של מה שקורה במערכת: **שורה אחת לכל בקשה
משמעותית**, עם המשתמש, הארגון, הפעולה, הנתיב, קוד הסטטוס ומשך הטיפול
במילישניות. המסך פתוח לבעלים של הארגון (`owner`) ולמנהל מערכת.

| מה יש בו | פירוט |
|---|---|
| כותרות | אירועים, משתמשים פעילים, פעולות שינוי, שגיאות, זמן תגובה ממוצע |
| רצועת שימוש | ספירת אירועים ל-14 הימים האחרונים |
| דירוגים | הפעולות הנפוצות, ומי המשתמשים הפעילים ביותר |
| טבלה | כל אירוע, עם פרטים שאפשר לפתוח בשורה |
| סינון | טווח זמן, חיפוש חופשי, פעולה, משתמש, שינויים בלבד / שגיאות בלבד |
| ייצוא | `/activity.csv` באותם סינונים, ו-`/activity/<id>` כ-JSON |

הכתיבה אוטומטית (`after_request`), ומסכים שיודעים לספר יותר מוסיפים פרטים
דרך `activity.note()` — מספר הרישוי שחופש וכמה תוצאות חזרו, כמה שורות
יובאו מ-CSV, איזה מק"ט נערך, למה ניסיון הזדהות נכשל. הפרטים נספחים
לאותה שורה, כך שיש אירוע אחד לכל פעולה של המשתמש.

**מה לא נכנס ללוג:** ערכי שדות של טפסים. נשמרים רק שמות השדות, ושדות
רגישים (סיסמה, טוקן, `csrf_token`) לא נשמרים אפילו בשם. רעש שאינו מספר
כלום — קבצים סטטיים, `/healthz`, והפולינג של מסכי הניהול — לא נרשם.

**גבולות ארגון:** בעלים רואה רק את מה שקרה בארגון שלו. מנהל מערכת יכול
לעבור לתצוגה חוצת-ארגונים (`?scope=all`), ורק הוא רואה גם את השימוש
האנונימי במסך הזיהוי, שאינו משויך לאף ארגון.

```bash
flask prune-activity   # מוחק אירועים ישנים מ-ACTIVITY_LOG_RETENTION_DAYS
```

## התקנה כאפליקציה

האפליקציה היא PWA וניתנת להתקנה למסך הבית — שימושי למכונאי שעובד
מהטלפון ומצלם חלקים.

- **אנדרואיד / Chrome**: כפתור "📲 התקן" בסרגל הניווט, או תפריט הדפדפן ← "התקן אפליקציה"
- **iPhone / Safari**: שיתוף ← "הוסף למסך הבית"

`app/routes/pwa.py` מגיש את המניפסט ואת ה-service worker **מהשורש** ולא
מ-`/static`, כי היקף ה-service worker מוגבל לנתיב שממנו הוגש.

**מה נשמר במטמון:** נכסים סטטיים בלבד. דפים תמיד נמשכים מהרשת, כי הם
מציגים מחירים, מלאי וזיהוי רכב חי — הגשה מהמטמון הייתה מציגה נתונים
ישנים כאילו הם עדכניים. בלי חיבור מוצג מסך ניתוק מפורש.

האייקונים נוצרים ב-`python scripts/make_icons.py`, וגרסת ה-service
worker נגזרת מה-commit כדי שדפדפנים ימשכו נכסים מחדש בכל פריסה.

## עמודות טבלת המק"טים

הטבלה ב-`/parts` אינה קבועה בקוד. **מנהל האפליקציה** קובע ב-`/admin/columns`
אילו עמודות מוצגות ובאיזה סדר, וההחלטה חלה על כל המשתמשים במערכת —
זו לא העדפה אישית אלא מה שנכון להראות.

| מה אפשר | איך |
|---|---|
| סדר | ▲/▼ לכל עמודה במסך הניהול |
| הוספה והסרה | מרשימת העמודות הזמינות, לצד המוצגות |
| מיון | אייקון שליד הכותרת. לחיצה ממיינת, לחיצה שנייה הופכת את הכיוון, והאייקון עצמו מראה את המצב |
| סינון | אייקון משפך שליד הכותרת, ומתחתיו נפתח השדה — טקסט, מספר או רשימה נפתחת, לפי סוג העמודה |

**מה יש ברשימה:** זהות המק"ט (מספר, מק"ט מקורי, שם, שם באנגלית, ברקוד,
יצרן, קטגוריה, סוג חלק, צד, מידות, משקל, אחריות), השכבה המסחרית של
הארגון (מחיר, עלות, מלאי, מלאי מינימלי, מיקום במחסן), הרכב שהחלק מתאים
לו (מתאים ל, יצרן רכב, דגם רכב), ושתי עמודות שסופרות את הקטלוג עצמו:

| עמודה | מה היא סופרת |
|---|---|
| **חלפים במאגר** | כמה מק"טים בקטלוג מתאימים לרכב של השורה הזאת. אותו מספר בדיוק שמסך `/stats` מציג לדגם, ובאותו כיווץ כתיב (`RAV 4` = `RAV4`). לחלק שמתאים לכמה רכבים — הרכב הרחב מביניהם |
| **תחליפים** | כמה מק"טים אחרים בקטלוג אפשר לשים במקומו: אותו כלל בדיוק כמו רשימת "מק"טים שקולים בקטלוג" שבכרטיס המק"ט |

### חשיבות החלק

שלוש עמודות נוספות עונות על "כמה זה חשוב", מתוך ספירת הצי של משרד
התחבורה — אותם מספרים שמסך `/stats` מציג, ובאותה הצלבה:

| עמודה | מה היא אומרת |
|---|---|
| **רכבים על הכביש** | כמה רכבים כאלה פעילים במרשם |
| **בטווח הקנייה** | מתוכם בני 4–12: מחוץ לאחריות ועדיין נוסעים — חלון האפטרמרקט |
| **רכבים למק"ט** | רכבים בטווח הקנייה על כל מק"ט שכבר יש לדגם. גבוה = פער גדול, כלומר הזדמנות |

לחלק שמתאים לכמה רכבים מוצג **הגדול מביניהם** — הרכב הנפוץ ביותר שהוא
משרת. סכום היה סופר פעמיים דגם שנספר לשני שמות בקטלוג.

**ההצלבה בין המרשם לקטלוג היא לוגיקה של פייתון ולא של SQL:** המרשם כותב
"טויוטה יפן" ו-"COROLLA HSD SDN", הקטלוג "טויוטה" ו-"COROLLA". הנרמול
הזה (שמגשר גם על "מזדה" מול "מאזדה") אינו ניתן לכתיבה ב-SQL בלי לשנות
אותו, ומספר שסותר את מסך הצי גרוע ממספר שחסר.

מה שכן: **הקטלוג כולו מחזיק כמה עשרות צמדי רכב בלבד** (39 בקטלוג
הנוכחי). ההצלבה נעשית בפייתון פעם אחת, והתוצאה — טבלה קטנה — נכתבת
לתוך השאילתה כ-`CASE`, כך שהמיון והסינון רצים בבסיס הנתונים על אותם
מספרים שהתא מציג. נמדד על 2,400 מק"טים מול צילום של 20,000 דגמים:
מיון 40–60 אלפיות, דף שלם 130.

מה שיקר — נרמול עשרות אלפי שורות המרשם — נשמר בזיכרון **לפי חותמת
הצילום**, שהיא זהות הצילום במערכת. צילום חדש פוסל את הזיכרון מאליו,
ולכן אין כאן מטמון שצריך לזכור לנקות.

**בלי ספירת צי טעונה** התאים מציגים "—" ולא 0: "לא ידוע" אינו "אין
רכבים כאלה".

שתי הספירות האלה מקובצות בתת-שאילתה אחת ולא נספרות מחדש לכל שורה.
הניסוח המתבקש — תת-שאילתה שרצה לכל מק"ט — לקח **שבע שניות** למיון לפי
תחליפים על קטלוג של 2,400 מק"טים, כי `lower()` מבטל את האינדקס והחיפוש
הופך לסריקה מלאה. אחרי הקיבוץ: 14 אלפיות. הערך שמוצג בתא מגיע מאותו
ביטוי שלפיו ממיינים, בשאילתה אחת לכל הדף — אחרת המספר בתא היה יכול
לסתור את הסדר שהוא עצמו יצר.

**סינון מספרי** מקבל מספר (`8`), טווח (`10-20`) או השוואה (`>10`, `<=50`).
מה שאי אפשר לקרוא כמספר פשוט לא מסנן — מסנן שהוקלד למחצה לא אמור לרוקן
את הטבלה.

המיון והסינון חיים יחד ונשמרים זה בזה: לחיצה על כותרת לא מאבדת את
הסינון, וסינון לא מחזיר את הטבלה למיון ברירת המחדל.

שני האייקונים יושבים בכותרת עצמה ואין שורת סינון נפרדת. שדה הסינון
נפתח *בתוך* הכותרת (`<details>`) ולא כחלונית צפה מעליה — חלונית הייתה
נחתכת בגלילה האופקית של הטבלה, דווקא בעמודות הקיצוניות. עמודה שכבר
מסוננת נפתחת מעצמה, אחרת הערך שסונן היה נעלם מהעין.

**בזמן שהשרת ממיין ומסנן** מופיע פס בראש הטבלה והנתונים הישנים
מתעמעמים. מיון וסינון אינם קורים בדפדפן אלא בבקשה לשרת, ובין הלחיצה
לבין הדף החדש המסך מציג את התוצאה הקודמת — בדיוק המצב שנראה תקוע.
הפס בלתי-מוגדר בכוונה: אין מה למדוד, ויש מה לומר. אותו חיווי עולה גם
במעבר בין עמודי התוצאות.

`app/part_columns.py` הוא מקור האמת: הכותרת, ביטוי המיון, סוג הסינון
והערך שמוצג בתא יושבים שם יחד, כך שעמודה חדשה היא רשומה אחת ולא סיור
בין תבנית, מסלול ושאילתה. הפריסה עצמה — הסדר ומה מוצג — נשמרת ב-DB
(`table_layouts`), ולכן שינוי שלה אינו דורש פריסה מחדש. אין שורה שמורה =
ברירת המחדל שבקוד, ולכן הטבלה עובדת ביום הראשון.

**מיון לפי מחיר הולך אחרי מה שכתוב בעמודה:** העמודה מציגה מחיר כולל
מע"מ, ולכן גם המיון והסינון מחשבים אותו — ולא את המחיר הגולמי, שיכול
לתת סדר אחר כשחלק מהשורות כבר כוללות מע"מ.

## גודל התצוגה

בתפריט הניווט — זה שמתקפל מאחורי ההמבורגר בטלפון — יש סעיף **הגדרות**
עם שני זוגות כפתורים, ‎+‎ ו-‎−‎:

| | מה זה משנה |
|---|---|
| **זום** | את הדף כולו, כמו הזום של הדפדפן: טקסט, כפתורים, מסגרות ותמונות גדלים יחד והפריסה נשארת כשהייתה |
| **גודל טקסט** | את גודל הבסיס שכל הטיפוגרפיה נמדדת ממנו: הטקסט והמרווחים שסביבו גדלים, התמונות לא, והשורות נשברות מחדש |

במוסך צריך את שניהם: זום כשמסתכלים על המסך ממרחק זרוע, גודל טקסט
כשרוצים יותר מק"טים על אותו מסך בלי לוותר על קריאוּת.

הטווח הוא 50%–180% לזום ו-80%–180% לטקסט, **בצעדים של 5%**. כפתור שהגיע
לקצה מושבת, ו"איפוס לגודל רגיל" מחזיר את שניהם ל-100%. הזום יורד עד חצי
כי שם נכנסת טבלת מק"טים שלמה למסך אחד.

**הגדלת טקסט מכווצת את הריפוד.** ריפוד נמדד ב-rem ולכן הוא גדל עם הגופן
מעצמו — והגדלה הייתה מוסיפה בעיקר רווח לבן ודוחקת שורות אל מחוץ למסך.
במקום זה הוא מתכווץ: ב-140% טקסט הריפוד הוא 80% מגודלו הרגיל, וב-180%
הוא 60%. כך ההגדלה מוסיפה אותיות, לא אוויר. הכיווץ חל על תאי הטבלאות,
על הכרטיסים, על רשימות ה-`list-group` ועל העטיפה של תוכן העמוד.

**ההגדרה שייכת למכשיר ולא לחשבון** (`localStorage`) — אותו אדם רוצה
גודל אחד על מסך המשרד ואחר על הטלפון, ולכן היא לא נשמרת בשרת.
`static/js/display.js` נטען ב-`<head>` ולא בסוף הדף: הוא מחיל את מה
שנשמר לפני הציור הראשון, אחרת הדף היה נפתח בגודל רגיל וקופץ לגודלו.
בגלישה פרטית שבה האחסון חסום המסך עדיין משתנה, פשוט לא נזכר.

Alembic הוא הבעלים היחיד של הסכימה. `create_all()` כבוי כברירת מחדל —
הוא לא יודע לשנות טבלה קיימת, ושתי מערכות שמנהלות את אותה סכימה סותרות
זו את זו.

```bash
flask db migrate -m "תיאור השינוי"   # אחרי שינוי במודלים
flask db upgrade                      # החלה
```

בפריסה זה רץ אוטומטית ב-`preDeployCommand`.

### מודל הנתונים
`Part` (מק"ט) · `Manufacturer` (יצרן חלפים) · `Category` (קטגוריה היררכית) ·
`CrossReference` (מק"ט מקורי/חלופי) · `Fitment` (התאמה לרכב) ·
`Supplier` + `PartSupplier` (ספקים, מחיר קנייה וזמן אספקה).

### ייבוא מחירוני ספקים

`/import` מקבל CSV ומעדכן לפיו את הקטלוג. שני כללים שקובעים מה
בטוח לשלוח לשם:

- **עמודה שאינה בקובץ אינה נמחקת.** מחירון עם `part_number` ו-`price`
  בלבד מעדכן מחיר ותו לא — לא את העלות והמלאי, ולא את שם החלק
  באנגלית, הברקוד, המשקל, התמונה או `part_type`. קודם כל שדה שלא
  הופיע בקובץ נקרא כריק ונדרס, ושלוש עמודות מחקו תשעה שדות.
  "לא נמסר" ו"נמסר ריק" הם שני דברים שונים: שדה שנשלח ריק כן מתנקה,
  וכך ניקוי שדה מהטופס ממשיך לעבוד.
- **שורה פגומה מפילה את עצמה בלבד.** היא מדווחת ברשימת השגיאות, וכל
  מה שנקרא לפניה ואחריה נשמר. המספרים שהמסך מציג בסוף הם מה שנכנס
  באמת לבסיס הנתונים.

המחירים והמלאי שבקובץ נכתבים לשכבה הפרטית של הארגון המייבא, לא
לקטלוג המשותף.

אותו כלל שומר גם על מסך העריכה: הטופס אינו מציג `image_url`, `notes`
ו-`dimensions`, ולכן הוא גם לא נוגע בהם. `notes` נושא את סימון המקור
של מה שהצנרת האוטומטית הכניסה — בלי הכלל הזה, מנהל שתיקן טעות כתיב
היה מוציא את המק"ט מ-`/admin/discovery/review`, התור שקיים בדיוק כדי
לסקור אותו.

## איתור רכב לפי מספר רישוי

`app/vehicles.py` פונה למאגר כלי הרכב הפתוח של משרד התחבורה
(`data.gov.il`) — חינמי ולא דורש מפתח. אם אין גישה לרשת, המודול נופל
אוטומטית לקובץ `data/vehicles_sample.json` עם עשרה רכבי דוגמה, כך שהזיהוי
ממשיך לעבוד. זו נפילה של *חיפוש הרכב* בלבד — המק"טים מגיעים מהקטלוג בכל
מקרה. מקור הנתונים מוצג במסך (`data.gov.il` מול `offline`), והמסך אומר
במפורש כשפרטי הרכב הגיעו מהקובץ המקומי.

### המרשם מפוצל לשני משאבים

זו הייתה הסיבה שרכב אמיתי החזיר "לא נמצא" בזמן שהמאגר ענה כראוי:
משרד התחבורה מפרסם את מספרי הרישוי **בשני משאבים** — "מספרי רישוי של
כלי רכב פרטיים ומסחריים" ו-"...המשך". הקוד שאל רק את הראשון, כלומר
שאל על חצי מהמרשם.

שלושת המאגרים שנשאלים כברירת מחדל, בלי שום הגדרה:

| מאגר | מזהה |
|---|---|
| רכב פרטי ומסחרי | `053cea08-…` |
| רכב פרטי ומסחרי · **המשך** | `0866573c-…` |
| ירדו מהכביש · ביטול סופי | `851ecab1-…` |

השלישי אינו מותרות: רכב שבוטל אינו במרשם הפעיל, ומכונאי שמחזיק אותו
בחצר עדיין צריך לו חלפים.

הראשון שמחזיר שורה עוצר את החיפוש — רכב שנמצא במאגר הראשון עולה בקשה
אחת, לא תשע. ויש תקציב זמן כולל (`GOV_LOOKUP_BUDGET`, 20 שניות):
מאגרים כפול אסטרטגיות זה הרבה בקשות, ו-gunicorn הורג בקשה אחרי 60 —
עדיף להיעצר ולומר "המאגר איטי" מאשר להיחתך באמצע בלי הודעה.

### מספר השלדה: שדה שאסור לאבד בשקט

`misgeret` הוא מה שמפעיל את החיפוש בקטלוג היצרן — בלעדיו כל התהליך
נופל לחיפוש לפי יצרן/דגם/שנה, שמדויק פחות. שם של עמודה במאגר פתוח
אינו חוזה: הוא משתנה בין גרסאות ובין משאבים. לכן הקריאה היא לפי
**רשימת שמות אפשריים** (`misgeret`, `mispar_shilda`, `shilda`, `vin`)
ולא לפי אחד — זה עולה כלום ומציל את השדה.

וכשהשדה בכל זאת ריק, `?debug=1` מחזיר את **השורה כפי שהמאגר החזיר
אותה** (`raw`). זה מה שמבדיל בין "העמודה לא קיימת במאגר" לבין "העמודה
קיימת וריקה לרכב הזה" — שתי בעיות שונות שנראות זהות על המסך.

### חיפוש חופשי לא יחזיר רכב אחר

`q=` מחזיר כל שורה שהמספר מופיע בה, ולא בהכרח בעמודת הרישוי. רכב שגוי
כאן אינו אי-דיוק — הוא חלפים שלא נכנסים לרכב. לכן כל שורה שחוזרת
נבדקת מול מספר הרישוי שביקשנו לפני שהיא מתקבלת.

### שתי מלכודות שנראות אותו דבר על המסך

**`mispar_rechev` הוא עמודה מספרית.** סינון CKAN עם המחרוזת `"10732802"`
מול עמודה מספרית לא מתאים — והמאגר מחזיר אפס שורות **בלי שגיאה**.
התוצאה היא "לא נמצא רכב" לכל מספר רישוי אמיתי, בזמן שרכבי הדוגמה
המקומיים ממשיכים לעבוד: כשל שנראה כמו מאגר ריק ואינו כזה. לכן יש שלוש
אסטרטגיות ולא אחת — סינון מספרי, סינון טקסטואלי, וחיפוש חופשי —
והראשונה שמחזירה שורה מנצחת.

**"המאגר לא ענה" אינו "אין רכב כזה".** אחת אומרת לנסות שוב, השנייה
אומרת שהמספר שגוי, וקודם שתיהן חזרו כ-`None` ונראו זהות. `lookup_detail`
מחזיר `status` (`found` / `not_found` / `unreachable`) ואת רשימת מה
שנוסה, המסך אומר את האמת, וה-API מחזיר 503 מול 404.

**מאגרים נוספים.** רכב שירד מהכביש, דו-גלגלי ורכב כבד יושבים במאגרים
נפרדים. הוספה היא הגדרה ולא פריסה:

```
GOV_VEHICLE_RESOURCES=<id>:ירדו מהכביש,<id>:דו-גלגלי
```

### כשמספר רישוי מחזיר "לא נמצא"

```bash
python scripts/plate_probe.py 107-32-802
curl "$APP/api/vehicle/10732802?debug=1"
```

שניהם מפרידים בין שלוש האפשרויות — המאגר לא נגיש, המאגר ענה ואין רכב
כזה, או שהשאילתה עצמה בנויה לא נכון — ומדפיסים מה כל אסטרטגיה החזירה.

**וכשהמאגר ענה ואין בו את הרכב**, הוא כנראה במאגר אחר. במקום לנחש
מזהים, האפליקציה מוצאת אותם:

```bash
python scripts/plate_probe.py 107-32-802 --discover
curl "$APP/api/vehicle/10732802?discover=1"
```

`discover_resources()` שואל את CKAN מי המאגרים, ומסנן לפי **קיום העמודה
`mispar_rechev`** — לא לפי שם. שם של מאגר משתנה, UUID משתנה, וקיום
עמודת מספר רישוי הוא מה שבאמת מגדיר "מאגר שאפשר לחפש בו רכב". לקבע
UUID בקוד זה לכתוב באג עתידי.

הסריקה יקרה — עשרות מאגרים, שאילתה לכל אחד — ולכן היא **אינה** רצה
בבקשה רגילה, רק כשמבקשים אותה במפורש. הפלט שלה הוא בדיוק מה שצריך
להיכנס ל-`GOV_VEHICLE_RESOURCES` כדי שהמסלול הרגיל ימצא את הרכב מיד
בפעם הבאה.

## קטלוג דגמי הרכב

התאמת מק"ט לרכב היא מה שמפעיל את החיפוש לפי מספר רישוי, ולכן היצרן והדגם
חייבים לבוא מרשימה סגורה: כשהם טקסט חופשי, "טויוטה" ו-"טויוטה יפן" הם שני
ערכים שונים וההצטלבות נכשלת. המקור הוא מאגר "תוצרים ודגמים" הפתוח של משרד
התחבורה — מעל 100 אלף רשומות, שורה לכל שנת ייצור, מכווצות לדגמים עם טווחי שנים.

שתי דרכים לייבא, שתיהן חולקות את `app/vehicle_import.py`:

```bash
python scripts/import_vehicle_models.py            # מהשורה, לפיתוח מקומי
python scripts/import_vehicle_models.py --file x.json   # מקובץ שכבר הורד
```

בפרודקשן דרך היישום: מסך `/admin/vehicle-import`, פתוח למי שכתובתו ב-
`SUPERADMIN_EMAILS`. הייבוא רץ **במנות** — כל בקשה מייבאת כמה עמודים ומקדמת
את נקודת ההמשך, כי משיכה של הכל בבקשה אחת חורגת מה-timeout של gunicorn.
ההתקדמות נשמרת בטבלה `vehicle_import_jobs` ולא בזיכרון, ולכן היא נראית לכל
ה-workers, שורדת נפילה או פריסה מחדש, וניתן להמשיך אותה מהנקודה שנעצרה.

## כמה רכבים מכל דגם על הכביש

`/stats` מציג את הפילוח: כמה רכבים פעילים יש מכל דגם בישראל, מהנפוץ לנדיר,
עם הנתח מכלל הצי, כמה מק"טים מהקטלוג מתאימים לדגם וכמה מהם **מתכלים**
(רפידות, דיסקים, מסננים, רצועות, מצתים ומגבים — `taxonomy.WEAR_TYPES`),
וקישור ישיר לחיפוש החלפים לאותו דגם. עמודות הספירה נשענות על אותו
`search_parts` שהחיפוש מריץ, כדי שהמספר בעמודה יהיה בדיוק מה שנפתח בלחיצה
עליו — הן נבנות ממפת התאמות אחת (`services.part_counts_for`) ולא משאילתה
לכל דגם, ולכן הן זולות גם למאות שורות. הן אינן בייצוא ה-CSV.

### לא כל רכב על הכביש הוא קונה

**חלון האפטרמרקט** הוא בערך 4–12 שנים: רכב חדש עדיין באחריות ובטיפולי
סוכנות, ורכב ישן מאוד כבר בקושי מטופל. הצילום שומר לכל דגם שלושה מונים
(`young`, `prime`, `old`) ולא רק את הסכום, והמסך מציג את **בטווח הקנייה**
לצד סך הרכבים. דגם עם 90 אלף רכבים שכולם מ-2024 אינו שוק; אותם 90 אלף
מ-2016 הם כן. סכום שלושת הדליים יכול להיות קטן מסך הרכבים — רשומה בלי
שנת ייצור אינה בשום דלי.

**רכבים למק"ט** הוא היחס שהופך את הטבלה לרשימת פעולה: כמה רכבים בטווח
הקנייה יש על כל מק"ט שבידינו. ערך גבוה = שוק גדול שאיננו מכסים. דגם בלי
מק"טים כלל מסומן "אין כיסוי" ולא באפס — אין מכנה, וזה הפער המרבי ולא
היעדר פער.

**מיון "הפער הגדול ביותר"** (`?sort=gap`) מדרג את `FLEET_GAP_MODELS`
הדגמים הגדולים בטווח הקנייה לפי `prime ÷ (מק"טים+1)`. הדירוג מוגבל
לדגמים הגדולים בכוונה: פער אצל דגם עם שלושים רכבים אינו הזדמנות, והוא
היה מציף את הרשימה. המקור הוא מרשם כלי
הרכב של משרד התחבורה — אותו מאגר שהזיהוי לפי מספר רישוי עובד מולו, שורה
לכל רכב פעיל, כשלושה מיליון שורות.

הקטלוג יודע אילו דגמים קיימים, לא כמה מהם על הכביש; דגם עם 90 אלף רכבים
ודגם עם 300 נראים אותו דבר ברשימת הדגמים, והם לא אותו דבר כשמחליטים איזה
מק"ט להחזיק במלאי.

הספירה נעשית בצד המאגר — `GROUP BY` אחד דרך נקודת ה-SQL של CKAN — ונשמרת
כצילום מצב בטבלה `fleet_model_counts`. המסך קורא מהטבלה ולא מהמאגר: ספירה
של שלושה מיליון רשומות אינה דבר שמחכים לו בתוך בקשת דפדפן.

**הצילום מוחלף רק כשהוא שלם.** ספירה חדשה נבנית לצד הישנה: כל שורה נושאת את
חותמת ההרצה שכתבה אותה, `/stats` ממשיך להציג את הצילום השלם האחרון, וההחלפה
היא רגע אחד בסוף. חצי ספירה שמוצגת כאילו היא הצי כולו אינה מספר חלקי אלא
מספר שקרי — ולכן גם הרצה שנעצרה או נכשלה נשארת מחוץ לתמונה עד שתושלם.

שתי דרכים להריץ, שתיהן חולקות את `app/fleet_stats.py`:

**מהיישום** — מסך `/admin/fleet-stats`, פתוח למי שכתובתו ב-`SUPERADMIN_EMAILS`.
זו הדרך בפרודקשן, שבה אין טרמינל. הספירה רצה **במנות**, כמו ייבוא קטלוג
הדגמים: כל בקשה מושכת עמוד ומקדמת את נקודת ההמשך, שנשמרת ב-`fleet_stats_jobs`
ולא בזיכרון — ולכן היא נראית לכל ה-workers, שורדת פריסה מחדש וניתן להמשיך
אותה מהנקודה שנעצרה.

**שני מסלולים, החלפה אוטומטית.** נקודת ה-SQL של המאגר אינה זמינה בכל
סביבה — היא מחזירה 404 — ולכן ההרצה מזהה זאת בעצמה ועוברת לסריקה מלאה:
מושכת את שורות הרכב עצמן (32 אלף לבקשה, ארבעה שדות בלבד, `sort=_id` כדי
שהעימוד יהיה יציב) וסופרת כאן. אותה תוצאה בדיוק, לוקח יותר זמן. מצב הספירה
נצבר על ההרצה עצמה בשדה דחוס ולא כשורות ביניים בטבלה, ורק בסוף הוא הופך
לשורות. בסריקה יש סה"כ אמיתי מהמאגר ולכן גם אחוז התקדמות אמיתי; בספירה
אצל המאגר אין למה להשוות, ושם המסך מראה מונים במקום אחוז מומצא.

**משורת הפקודה** — לפיתוח מקומי ולטעינה מקובץ:

```bash
python scripts/vehicle_stats.py --load          # ספירה, CSV וטעינה למסד
python scripts/vehicle_stats.py --min-count 100 # רק דגמים עם 100 רכבים ומעלה
python scripts/vehicle_stats.py --scan --load   # כשנקודת ה-SQL של המאגר סגורה
python scripts/vehicle_stats.py --file rechev.csv  # מקובץ המאגר שהורד ידנית
```

שלושת המסלולים מייצרים את אותן שורות בדיוק. `--scan` מדפדף במאגר בעמודים
של אלף וסופר מקומית — אותה תוצאה, הרבה יותר לאט, ולכן הוא מסלול חירום
ולא ברירת מחדל. הפילוח יורד גם כ-CSV מהמסך עצמו (`/stats.csv`), באותו
סינון שמוצג.

## כשהמרשם והקטלוג קוראים לאותו רכב בשני שמות

שני הצדדים לא מסכימים על שמות, ובכל פעם שההשוואה נכשלת נוצר "אין
כיסוי" מדומה — בדוח, וגרוע מכך גם בזיהוי לפי מספר רישוי:

- **שם הדגם.** לפעמים שם הקטלוג ארוך יותר (`COROLLA VERSO` מול
  `COROLLA`), ולפעמים דווקא שם המרשם (`COROLLA HSD SDN`). ההתאמה היא
  בשני הכיוונים, בארבעה סעיפים:

  | | |
  |---|---|
  | אותו שם אחרי כיווץ | `RAV 4` = `RAV4` |
  | שם המרשם הוא **מילה שלמה** בשם הקטלוג | `3` בתוך `MAZDA 3` |
  | שם הקטלוג הוא מילה שלמה בשם המרשם | `COROLLA` בתוך `COROLLA HSD SDN` |
  | שם הקטלוג הוא קידומת, ואחריה **אין ספרה** | `CX-5` מול `CX-5 AWD` |

  שני הסעיפים האחרונים הם מה שמונע מדגם למשוך את החלפים של דגם אחר.
  ההשוואה הייתה "מוכל בתוך", וכך `CX-3` משך את החלפים של `CX-30`
  ולהפך — 111 התאמות לדגם הלא נכון בקטלוג הזה, ועוד שקטות שחיכו לגדול
  (`CEED` מול `PROCEED`, `i10` מול `i100`). מילה ולא הכלה, וספרה
  שנמשכת פוסלת: בשמות רכב ספרה בהמשך היא **דגם אחר**, ומילה בהמשך
  היא רמת גימור.

  `MIN_MODEL_PREFIX` חל על סעיף הקידומת בלבד — שם קטלוג קצר משלוש
  אותיות אינו קידומת אלא צירוף אותיות.

  הכלל כתוב פעמיים: `model_matches_name` בפייתון ו-`_model_matches`
  כביטוי SQL, כי חלק מהמסכים מסננים בבסיס הנתונים וחלק בזיכרון.
  `tests/test_model_matching.py` מריץ את שניהם על אותם נתונים ומוודא
  שהם מחזירים בדיוק אותו דבר — בלי זה אפשר לתקן צד אחד ולהשאיר את
  השני מאחור, והמסך יציג מספר אחד ויסדר לפי אחר.
- **שם היצרן.** המרשם כותב "מזדה" והקטלוג "מאזדה" — אותו יצרן, אֵם
  קריאה אחת הבדל. `normalize_make` מפילה א' ואותיות כפולות ומשווה את
  מה שנשאר. על שנים-עשר היצרנים שבקטלוג היא אינה ממזגת שניים לאחד,
  ולכן היא מגשרת על כתיב בלי להמציא התאמות.

בדירוג הפערים השורות מקובצות לדגם אחד (`grouped_by_model`): לאותו דגם
יש כמה קודי דגם, ולפעמים גם כמה כתיבי יצרן ("מזדה יפן" ו-"מזדה
תאילנד"), ולקטלוג אין הבחנה ביניהם — הם היו מופיעים כשורות נפרדות עם
אותו מספר בדיוק.

## המנוע: מסומן, לא מסונן

חלף מתאים למנוע ולא לשם מסחרי, ולכן ההצטלבות מנסה לזהות גם אותו. אבל
נתוני המנוע בשני הצדדים לא מסתדרים בקלות:

- בקטלוג רק כחמישית מההתאמות מציינות מנוע בכלל, ומי שכן מציין כותב
  בשני כתיבים — רובו נפח ורמת מנוע (`1.4 TSI`), ומיעוטו קוד יצרן
  (`2ZR-FAE`).
- המרשם מוסר קוד יצרן בלבד (`degem_manoa`). הנפח מגיע מקטלוג הדגמים
  שלנו לפי (יצרן, קוד דגם), ומתורגם לכתיב של הקטלוג: 1398 סמ"ק → `1.4`.

`vehicle_engine_terms` מחזיר את שני המונחים, כי כל אחד מהם מוצא חלק אחר
של הקטלוג, וההשוואה מכווצת (`2ZR-FAE` = `2ZRFAE`).

**ומה שנעשה עם זה הוא סימון ולא סינון.** סינון לפי מנוע היה מסתיר מק"ט
נכון שנכתב בכתיב האחר, או כזה שלא ציין מנוע כלל — הפסד גרוע בהרבה
מרשימה קצת ארוכה. לכן כל המק"טים נשארים, אלה שההתאמה שלהם מצהירה על
המנוע של הרכב עולים לראש ומסומנים "מנוע תואם", והשאר ממשיכים להופיע
אחריהם.

הסינון המפורש (`/parts?engine=`) כן מצמצם — אבל גם הוא מכבד את ההבחנה
בין "מנוע אחר" לבין "לא צוין מנוע": התאמה שלא אמרה כלום על מנוע נשארת,
כי היעדר מידע אינו הצהרה שהחלק לא מתאים. קודם לכן היא נמחקה, ואיתה רוב
הקטלוג.

## הגילוי מכוון לפי הפער, לא לפי ניחוש

`/admin/discovery` מחפש מק"טים באינטרנט לפי (יצרן, דגם, סוג חלק). כשלא
מוקלד דגם, המטרות נבחרות **מדירוג הפערים** — כמה רכבים בטווח הקנייה יש
לדגם, חלקי המק"טים שכבר יש לנו עבורו (`fleet_stats.gap_ranking`, אותו
חישוב בדיוק שמאחורי `?sort=gap` במסך).

קודם לכן הן נבחרו לפי מספר הווריאנטים בקטלוג הדגמים — "הפרוקסי היחיד
לפופולריות שיש", כלשון ההערה שהייתה בקוד. מאז נוספה ספירה אמיתית של
מיליוני רכבים, ולכן הגילוי רץ היום על השוק הגדול שאינו מכוסה במקום על
דגם שבמקרה יש לו הרבה קודי דגם. לחפש מק"טים לדגם עם מאתיים מק"טים
קיימים זה בזבוז; לדגם עם חמישים אלף רכבים ואפס מק"טים זו העבודה.

הזוגות מוחזרים בכתיב הקטלוג (`services.catalog_make`), כדי שהתאמות
חדשות יישבו לצד הקיימות ולא יפתחו כתיב שני לאותו יצרן. בלי צילום צי
המסך נופל לפרוקסי הישן — גילוי שמכוון פחות טוב עדיף על מסך שלא עושה
כלום — והוא אומר במפורש לפי מה נבחרו המטרות.

## שליפה חיה: כשאין מק"ט בקטלוג

עד עכשיו הזרימה נעצרה ב"אין מק"ט מסוג זה בקטלוג עבור הרכב הזה". היום
היא ממשיכה: הרכב כבר מזוהה, ולמרשם יש את **מספר השלדה** שלו
(`misgeret`) — וזה מפתח חיפוש אחר לגמרי ממה שהיה לנו.

**למה שלדה ולא יצרן+דגם.** חיפוש לפי דגם מחזיר את מה שמתאים *לדגם*.
אותה קורולה 2016 קיימת עם שני מנועים, ושני מסננים שונים. חיפוש לפי
שלדה מחזיר את מה שמתאים *לרכב הזה*, וזה ההבדל בין מק"ט שנכנס לרכב
לבין מק"ט שחוזר למחסן.

### שני עולמות של מק"ט, ומספר אחד שמגשר ביניהם

```
מספר שלדה  →  קטלוג היצרן   →  מק"ט מקורי + תרשים פיצוץ
                                        ↓
                            מספר OE = מפתח הגישור
                                        ↓
                  קטלוג חלופים  →  מק"טים חלופיים + תמונת מוצר
```

מכונאי לא מזמין מק"ט מקורי — הוא מזמין את החלופי, ומספר ה-OE הוא מה
שמאשר לו שזה אותו חלק. הציר הזה כבר היה בסכימה
(`CrossReference(ref_type="OEM")`); מה שחסר היה מי ימלא אותו מתוך
שלדה. גם התמונות באות משני העולמות: תרשים פיצוץ מראה *איפה החלק
ברכב*, תמונת מוצר מראה *איך הוא נראה*.

### הסדר שבו נשאלות השאלות

```
① הקטלוג המקומי   → יש מק"ט לרכב הזה? מחזירים, בלי לצאת לרשת
② מטמון התשובות   → נשאלנו כבר על הדגם הזה? מחזירים
③ המקורות         → קטלוג היצרן, ואחריו קטלוג החלופים
④ אימות ושמירה    → מה שעבר נכנס לקטלוג. החיפוש הבא נענה בשלב ①
```

הקטלוג **גדל מכל חיפוש של משתמש**. אחרי חודש רוב השאילתות נענות
מקומית, והיציאה לרשת הופכת לשולית — וזה גם מה שהופך את התהליך לבר-קיימא
וגם מה שמצדיק אותו.

### שער אישור בין מקור למקור

שלב ③ אינו רץ עד הסוף מעצמו. **כל מקור נעצר, מציג את מה שמצא, ושואל
אם להמשיך לבא אחריו:**

```
Laximo → "04152-YZZA1 · מקורי לפי שלדה"
         [ המשך ל-TecDoc ]  [ מספיק, זה מה שחיפשתי ]
```

הסיבה היא שהשאלה השנייה אינה המשך של הראשונה אלא שאלה אחרת: הראשונה
היא "מה המק"ט המקורי לרכב **הזה**", והשנייה היא "מה אפשר להציע במקומו".
מכונאי שמזמין מהסוכנות סיים אחרי הראשונה, וכל מקור נוסף הוא בקשת רשת,
קריאת מודל, והמתנה — TecDoc בונה את התוצאה ב-JavaScript ולוקח עשרות
שניות. הוא גם נספר במכסה היומית של הארגון (`LOOKUP_DAILY_LIMIT`).

**ההפסקה אינה פוגעת בתוצאה.** TecDoc מחפש לפי מספר ה-OE ש-Laximo
הוציא, וזה יושב ב-`job.results` — עמודה בטבלה, לא זיכרון תהליך. הפסקה
של שנייה או של שעה מגיעה לאותה תוצאה בדיוק, וגם `gunicorn` שהרג את
הבקשה באמצע אינו משנה דבר.

**מה שנעצר אינו נכנס למטמון.** תשובה חלקית היא חלקית *בבחירה של מי
ששאל*, ושמירתה הייתה מגישה אותה למכונאי הבא כאילו זה כל מה שיש — בלי
שהוא בחר בכך ובלי דרך לדעת. מה שכן נשמר הוא מה שנכנס לקטלוג תוך כדי:
`parts_discovery.save` רץ לכל מקור בנפרד, ולכן חיפוש חוזר לאותו רכב
נענה בשלב ① ממה שהמקור הראשון כבר הביא.

עצירה נרשמת בלוג השימוש כ-`lookup.stopped`, עם המקור שאחריו נעצרה ומה
שדולג — כך שאפשר לראות אם משתמשים עוצרים כהרגל, ואם כן, לשקול סדר
מקורות אחר.

### מפתח המטמון הוא דגם, לא רכב

`vin_key` הוא שמונת התווים הראשונים של השלדה ותו שנת הדגם: יצרן, תיאור
הדגם ושנה — בלי המפעל ובלי המספר הסידורי. הקורולה החמישים מאותו דגם לא
שולחת בקשה לאף אתר, ושום מזהה של רכב מסוים לא נשמר בדרך. לרכב בלי שלדה
במרשם המפתח נופל לזהות הרישומית (`reg:` + יצרן/דגם/שנה/מנוע), והמסך
אומר שהחיפוש מדויק פחות.

### למה זה עבודה ולא בקשה

בקשת רשת לאתר חיצוני ואחריה קריאה למודל, כפול מספר המקורות — ו-gunicorn
הורג בקשה אחרי 60 שניות. לכן אותו דפוס שכבר עובד פעמיים בקוד
(`DiscoveryJob`, ייבוא דגמי הרכב): `LookupJob` בטבלה, **מקור אחד לכל
בקשת HTTP**, והדפדפן מסקר. ההתקדמות יושבת ב-DB, כך ששני ה-workers
רואים אותה.

### שני הספקים: Laximo ו-TecDoc

אלה לא אתרים אקראיים - הם שני הצדדים של אותו ציר:

| ספק | מה הוא נותן | מפתח הכניסה |
|---|---|---|
| **Laximo** | קטלוגי היצרן (OEM), עם תרשימי פיצוץ | **מספר שלדה** |
| **TecDoc** (TecAlliance) | חלופים: מי מייצר תחליף למה, עם תמונת מוצר | **מספר OE** |

Laximo הופך את ה-`misgeret` שהמרשם נתן לרכב מדויק ולמק"ט מקורי; TecDoc
לוקח את המספר הזה ואומר מה המוסך יכול להזמין במקומו. זו הסיבה שהסדר
ב-`CATALOG_SOURCES` הוא `laximo,tecdoc` ולא הפוך — היפוך משאיר את השלב
השני בלי מפתח.

**לשניים אין אותו מספר מסלולים.**

**TecDoc** מחזיק שניים, ואותו פלט משניהם:

- `api` — השירות הרשמי, עם `TECDOC_API_KEY` ומזהה ספק. זה המסלול
  המורשה, והיחיד שמתאים לשימוש מסחרי בתמונות ובנתונים.
- `web` — הקטלוג בדפדפן, דרך Playwright. למי שיש לו גישת web בלבד.

`TECDOC_MODE` בוחר; `auto` (ברירת המחדל) הולך ל-API כשיש אישורי גישה
ולדפדפן כשאין. גוף הבקשה **משתנה בין חבילות רישיון**, ולכן הוא משתנה
סביבה (`TECDOC_QUERY`) ולא קבוע בקוד — התאמה לחשבון שלך היא שינוי
הגדרה, לא פריסה.

**Laximo** מחזיק אחד: `web` בלבד. היה כאן גם מסלול API (בקשה חתומה
ב-`md5(command + password)` כסיסמת Basic Auth, עם
`LAXIMO_LOGIN`/`LAXIMO_PASSWORD`), והוא הוסר. הסיבה אינה טכנית אלא
שהוא דרש חשבון שאין, וקוד שאי אפשר להריץ אינו מסלול גיבוי — הוא ענף
מת שכל קורא צריך לפסוח עליו ושכל בדיקה מזייפת. אין ל-Laximo
`LAXIMO_MODE`, ואם ייפתח חשבון אפשר להחזיר את המסלול מההיסטוריה.

### מי מביא את הדף

שלוש דרכים מאחורי בורר אחד (`CATALOG_FETCHER`), ו-`auto` בוחר את הטוב
ביותר שזמין:

| מסלול | מתי | מה הוא נותן |
|---|---|---|
| `scraperapi` | יש `SCRAPERAPI_KEY` | עוקף חסימת IP של ענן, מריץ JS בצד שלהם |
| `browser` | יש Chromium מותקן | דף מלא, ומילוי טפסים |
| `direct` | תמיד | `urllib` — מספיק רק לאתר שאינו בונה את התוצאה ב-JS |

**למה ScraperAPI רלוונטי כאן.** אתרי קטלוג מסחריים חוסמים טווחי כתובות
של ספקי אירוח, ו-Railway הוא בדיוק כזה — כלומר Chromium שרץ אצלנו עלול
פשוט לקבל 403. השירות מסובב כתובות ביתיות, ו-`render=true` מריץ את
ה-JavaScript אצלם: זה מייתר את Chromium בתמונה, ואיתו את כל סיפור
מספרי ה-build וה-thread הייעודי.

מה שהוא **לא** נותן: מילוי טופס ולחיצה. הוא מביא כתובת ומחזיר HTML.
לכן בקשה שהוגדר לה `*_WEB_INPUT` עוברת לדפדפן גם כשהבורר הוא ScraperAPI
— אחרת היינו מביאים בשקט את דף החיפוש הריק, וזה כשל שקשה לראות: יש
תשובה, היא פשוט לא נכונה.

**המחיר: זמן.** עיבוד עם `render=true` לוקח עשרות שניות, ובקשת שלב אחת
היא הבאה ועוד קריאה למודל. לכן עם המסלול הזה צריך `WEB_TIMEOUT=90`.

**מה שלא משתנה:** `robots.txt` נבדק גם כאן — השירות מביא בשמנו, ולכן
מה שאסור לנו אסור גם דרכו.

`Laximo` ו-`TecDoc` מסומנים `needs_js = True`, ולכן אם המסלול היחיד
שנשאר הוא `direct` הם מדווחים שאינם זמינים במקום להביא שלד ריק
ולהחזיר "לא נמצא" שנשמע אמין.

בדיקת חשבון מהירה:

```bash
python scripts/catalog_probe.py --account
python scripts/catalog_probe.py --plate 12345678 --fetcher scraperapi --save out.html
```

### למה דפדפן אמיתי

Laximo ו-TecDoc בונים את התוצאה ב-JavaScript אחרי טעינת הדף. `urllib`
מקבל מהם שלד ריק, ולכן מסלול ה-`web` רץ ב-Chromium דרך Playwright —
אותו דף שאדם היה רואה. שלושה דברים ש-`catalog_sources/browser.py` פותר:

1. **איתור הדפדפן.** ל-Playwright יש מספר build משלו, ולתמונה שמריצה
   אותנו עשוי להיות אחר; `launch()` נכשל אז על נתיב שלא קיים. המודול
   מאתר את מה שבאמת מותקן ומעביר אותו במפורש.
2. **thread ייעודי.** ה-API הסינכרוני של Playwright קשור ל-thread שיצר
   אותו, ו-gunicorn כאן רץ ב-`gthread` — בקשות מגיעות מ-threads שונים.
   מנעול בלבד היה נותן דפדפן שנוצר בבקשה הראשונה ונשבר בשנייה. לכן
   הדפדפן חי ב-thread אחד קבוע וכל שליפה נשלחת אליו. זה גם מסדר את
   הבקשות בטור, מה שממילא רצוי מול אתר של מישהו אחר.
3. **מצב מזוהה.** `CATALOG_STORAGE_STATE` הוא קובץ עוגיות שנשמר פעם
   אחת, וכל שליפה מכאן והלאה נכנסת איתו.
4. **חיפוש שאינו כתובת.** לא בכל קטלוג מגיעים לתוצאה עם פרמטר בכתובת.
   `LAXIMO_WEB_INPUT`/`TECDOC_WEB_INPUT` הם השדה שממלאים, ו-`..._SUBMIT`
   הכפתור שלוחצים — כמו אדם. בלי `SUBMIT` נשלח Enter.

**אורח, לא בוט.** `robots.txt` נבדק גם במסלול הדפדפן ולא רק בהבאה
הפשוטה, הודעת ההסכמה על עוגיות נסגרת כדי שהדף ייבנה, וה-User-Agent הוא
של דפדפן אמיתי — דף שמוגש ל-`HeadlessChrome` אינו הדף שצריך לקרוא.
אין כאן עקיפה של הזדהות או של חסימה: מה שדורש חשבון ימשיך לדרוש חשבון.

Playwright יושב ב-`requirements.txt` הרגיל, לא בקובץ נפרד: בלי חשבון
API אצל הספקים זה **המסלול היחיד שיש**, ותלות שאפשר לשכוח להתקין היא
פיצ'ר שכבוי בפרודקשן בלי שאיש שם לב.

### מה עוד צריך כדי שזה יעבוד

**כתובות הקטלוג בקוד הן השערות שלא אומתו.** `LAXIMO_WEB_URL` וגם
`TECDOC_WEB_URL` נכתבו כברירת מחדל סבירה, ולא נבדקו מול האתרים.
בפועל `laximo.ru` מחזיר **404** על הנתיב שבברירת המחדל — הוא אינו
קיים שם:

```
כתובת הקטלוג שהוגדרה אינה קיימת באתר (404).
https://laximo.ru/search?type=vin&q=VF3M45GFRLS125956
```

כלומר כל עוד לא הוגדרה כתובת אמיתית, כל שליפה נכשלת — וצורכת בדרך
קרדיט ScraperAPI ומכסה יומית. חיפוש לפי שלדה אצל Laximo הוא מוצר
בתשלום, ואין ודאות שקיימת לו כתובת ציבורית כלשהי; ייתכן שהמסלול
הנכון הוא חשבון API (`LAXIMO_LOGIN`/`LAXIMO_PASSWORD`, שהוסר
מההיסטוריה וניתן להחזיר) או ספק OEM אחר לגמרי.

מה שכן נכון כבר עכשיו: **הכישלון אומר את שמו.** המסך מבחין בין
"המקור ענה ואין לו את החלק" לבין "המקור נכשל", ומראה את הסיבה ואת
הכתובת שנוסתה — במקום להדביק מאתיים תווים של HTML.

`pip install playwright` מתקין את הספרייה אבל **לא מוריד את Chromium**.
לכן `browser_available()` בודק גם שקובץ הדפדפן קיים על הדיסק, ומי
שמנסה בלעדיו מקבל את הפקודה להקליד ולא traceback של Playwright:

```bash
playwright install chromium                 # פיתוח מקומי
playwright install --with-deps chromium     # בפריסה, בשלב הבנייה
```

### יומן החקירה: "פרטי החיפוש"

`לא החזיר מק"ט` יכול להיות שלושה דברים שונים לגמרי, ועל המסך הם נראים
זהים:

1. האתר הפנה אותנו לדף הבית — חיפוש השלדה לא הוכר.
2. הגענו לדף התוצאות הנכון, והחלק פשוט לא קיים לרכב הזה.
3. הדף חזר כשלד ריק, כי התוכן שלו נבנה ב-JavaScript.

לכל אחת מהן תיקון אחר, ולכן כל שלב בדרך רושם שורה: הכתובת שנפתחה,
הכתובת שאליה **הופנינו בפועל**, קוד ה-HTTP, גודל הדף וכותרתו, כמה
נשאר אחרי הצמצום, פתיחת הטקסט שנשלח למודל, ומה המודל החזיר — כולל
האם הדף אישר שזה הרכב הנכון.

היומן מגיע למסך בתוך `פרטי החיפוש`, סגור כברירת מחדל (מכונאי מחפש
מק"ט, לא כתובות) ופתוח בלחיצה אחת, עם כפתור העתקה. אותו יומן בדיוק
מודפס גם מ-`catalog_probe.py`, וגם כשהשליפה נכשלה — שם הוא הכי שווה.

שתי השורות הראשונות בו עונות על השאלה הראשונה בכל חקירה — *מה בעצם
רץ*: אילו מקורות, באיזה סדר, ובאיזה מסלול הבאה. `CATALOG_SOURCES`
ו-`CATALOG_FETCHER` נקראים בזמן ייבוא, ואין דרך אחרת לדעת מהמסך אם
משתנה סביבה שהוגדר אכן נתפס.

כיבוי והגבלות: `CATALOG_TRACE`, `CATALOG_TRACE_LINES`,
`CATALOG_TRACE_PREVIEW`, `LOOKUP_LOG_CHARS`, `LOOKUP_LOG_LINES`
(ראה `.env.example`).

### כתובת חיפוש השלדה, וכשהיא שגויה

`EPC_VIN_URL` היא הדבר השביר ביותר במקור ה-OEM: אתרי קטלוג לא מתעדים
את מבנה הכתובות שלהם, והכתובת היא ניחוש עד שרואים אותה עונה.

**הכישלון השקט שהיה כאן.** `https://7zap.com/en/search/?q={vin}` החזיר
`HTTP 200` ודף תקין לגמרי — דף הבית של האתר. הכתובת פשוט לא קיימת שם,
והאתר הקפיץ אותנו לשורש. על המסך זה נראה `לא מצא מק"ט לחלק הזה ברכב
הזה`, שהוא לא רק לא נכון אלא גם כיוון שאי אפשר לפעול לפיו: החלק קיים,
הכתובת שגויה.

לכן הקוד משווה עכשיו את הכתובת שביקשנו לכתובת שנחתנו בה
(`bounced_to_ancestor`). הפניה ש**מרחיבה** — לשורש, או שבולעת את
השאילתה שנשאה את השלדה — היא שגיאת הגדרה, ומדווחת ככזו, בשם המשתנה.
הפניה ש**מעמיקה** לתוך הקטלוג היא חיפוש שהצליח, ואינה נוגעת בכלום.
הדף הזה גם לא נשלח למודל: הוא כבר ידוע כלא רלוונטי, ואין סיבה לשלם
עליו קריאה.

**כמה מועמדות בבת אחת.** `EPC_VIN_URL` מקבלת כמה תבניות מופרדות ב-`|`,
והן מנוסות לפי הסדר עד שאחת עונה. זה מה שהופך "לנחש, לפרוס, לבדוק"
מלולאה של שעה לריצה אחת שהיומן שלה אומר איזו תבנית עבדה:

```bash
EPC_VIN_URL='https://a.com/vin/{vin}|https://b.com/search?q={vin}'
```

תבנית שאין בה `{vin}` מסומנת ביומן — היא לא יכולה להחזיר תשובה *לרכב
הזה*. תבנית אחת שענתה "אין כאן כזה חלק" גוברת על אחות שנפלה: אחרת
תבנית שבורה ברשימה הייתה מסתירה תשובה אמיתית.

### מי מביא את הדף — וזה חייב להיות אותו אחד לכולם

לכל מקור יש `fetcher` שאפשר להזריק (בדיקות, `catalog_probe`), ובלעדיו
הוא חייב לקרוא ל-`default_fetcher()` — הפונקציה שמסתכלת על
`CATALOG_FETCHER` ועל `SCRAPERAPI_KEY` ומחזירה את המסלול הנכון.

**זו הייתה תקלה אמיתית, ולא הערה תיאורטית.** `epc` ו-`aftermarket`
קראו ל-`fetch` (urllib) ישירות. `SCRAPERAPI_KEY` היה מוגדר, המסך דיווח
`מסלול הבאה: scraperapi`, והבקשה בכל זאת יצאה מכתובת הענן של Railway
ישירות אל האתר — ו-Cloudflare החזיר `403`. `laximo` ו-`tecdoc` עשו את
זה נכון מהיום הראשון, ולכן הפער התגלה רק כששני האחרים הופעלו.

היומן עצמו הטעה: הוא הדפיס את המסלול ה**מוגדר**. עכשיו כל מקור רושם
את שם ההבאה שבאמת רצה (`ScraperApiFetcher`, `BrowserFetcher`,
`ישירה (urllib)`), ושורות ההבאה עצמן נושאות את ההבדל — `→ ScraperAPI:`
לעומת `→ הבאה ישירה:`.

אם `403` חוזר גם דרך ScraperAPI, הלבן הבא הוא `SCRAPERAPI_PREMIUM=1`
(פרוקסי מגורים) — וההודעה על 403 כבר אומרת את זה.

### תקציב הזמן — שלושה מספרים שחייבים להסתדר יחד

```
SCRAPERAPI_TIMEOUT  +  CATALOG_MODEL_BUDGET  <  WEB_TIMEOUT
```

`WEB_TIMEOUT` הוא הזמן ש-gunicorn נותן לבקשה שלמה, ובקשת שלב אחת היא
הבאה **ועוד** קריאה למודל. אם ההבאה לבדה רשאית לרוץ עד התקרה, אין זמן
למודל — ובמקרה הגרוע gunicorn הורג את העובד באמצע, והמשתמש לא מקבל
אפילו הודעת שגיאה. הקוד מזהה הגדרה כזו ומזהיר עליה ביומן, בשורה שצמודה
לבקשה עצמה.

**נבדק בשטח:** PartSouq עם `render=true` לא סיים ב-40 שניות (ברירת
המחדל). צירוף שמשאיר מקום: `WEB_TIMEOUT=120`, `SCRAPERAPI_TIMEOUT=90`.

פקיעת זמן **אינה** "לא נגיש", וההודעה מבדילה: השירות ענה בסדר גמור,
הוא פשוט לא סיים בזמן שהקצבנו — וזו הגדרה, לא תקלת רשת. ההודעה אומרת
איזה מספר לשנות, ומציעה גם את `SCRAPERAPI_RENDER=0` כשהוא דלוק.

### מה נבדק בפועל

| אתר | תבנית | תוצאה |
|---|---|---|
| PartSouq | `…/en/search/all?q={vin}` | **עובד.** שלדת טויוטה מחזירה עמוד קטלוג מזוהה, עם קבוצות ותרשימים |
| 7zap | `…/en/search/?q={vin}` | **לא קיים.** 200 והקפצה לדף הבית |
| 7zap | כל כתובת | תרשימים ומספרי חלקים **נעולים מאחורי מנוי** |
| catalogs-parts.com | — | ספרייה שמפנה ל-7zap, ומשם למנוי |

לכן ברירת המחדל היא PartSouq. **הגבול שלה:** הקטלוגים הם טויוטה,
לקסוס, ניסאן, אינפיניטי, מיצובישי, סובארו, יונדאי, קיה, סוזוקי,
מאזדה, הונדה, איסוזו, רנו, וולוו, קרייזלר, ג'יפ, דודג' ורם — ואין
שם פיג'ו, סיטרואן, סקודה ופולקסווגן. האתר עצמו מודיע שפענוח שלדה
נתמך כרגע לטויוטה בלבד.

שלדה שאינה מוכרת שם מחזירה `Nothing found` ב-200 ובלי הפניה — כלומר
הענף הנכון של "האתר ענה, אין כאן כזה חלק", ולא כשל.

### שליפה דטרמיניסטית, פענוח במודל

הקוד בונה את הכתובת מהשלדה, מביא את הדף, מצמצם אותו ומגביל קצב.
**המודל קורא את הדף** ומחזיר את המק"ט. החלוקה הזו נבחרה משתי סיבות
שכבר נצרבו בקוד הזה:

- סלקטורים נשברים בכל שינוי עיצוב, ובשקט. דף שהמודל קורא לא נשבר.
- גרידה תמימה מכניסה חלקים של רכב אחר — בעמוד הקורולה נמצא מסנן
  שהתיאור שלו אומר CHERY AMULET (ראה `parts_discovery`).

מה ששומר על זה חי הוא ה-fixtures: `tests/fixtures/*.html` הם עותקים
שמורים של דפי קטלוג, והבדיקות רצות עליהם **בלי רשת ובלי מפתח**.

### מה נכנס לקטלוג ומה רק מוצג

האימות הוא אותו אימות של הגילוי (`parts_discovery.validate`) — הוא
פוסל מק"ט בלי יצרן, מק"ט שמוזכר בו יצרן רכב אחר, ומועמד שהמודל עצמו
לא היה בטוח בו. מה שעבר נכתב לקטלוג עם התאמה מדויקת (מנוע, שנה,
וריאנט) וסימון מקור משלו (`SOURCE_MARK` נפרד מזה של הגילוי, כדי
ששתי הצנרות יהיו ניתנות למחיקה בנפרד).

מה שלא עבר **מוצג ומסומן, ולא נכתב**. שלוש רמות ולא "נמצא/לא נמצא":

| סימון | מה זה |
|---|---|
| מקורי · לפי שלדה | קטלוג היצרן קשר את המק"ט לשלדה הזו |
| חלופי מאומת | קטלוג החלופים קשר אותו למספר המקורי |
| לא אומת | מועמד שנפסל, עם סיבת הפסילה לצידו |

מכונאי שרואה שלוש אפשרויות עם רמות ודאות שונות מחליט לבד. מכונאי
שרואה "לא נמצא" מרים טלפון.

**המק"ט המקורי ותרשים הפיצוץ.** כשהמקור הוא קטלוג היצרן, מה שנמצא
אינו "שתי תוצאות" אלא *המק"ט המקורי לשלדה הזאת* — וכך כתוב בכותרת.
לצידו, כשהקטלוג מספק אותו, תרשים הפיצוץ: הסכמה שבה החלק מסומן במקומו
ברכב, ברוחב מלא ולחיצה פותחת בגודל מקורי.

**מקור שלא מצא אומר את זה.** שלב שהסתיים אינו שלב שמצא, ולכן המסך
מבחין בין שלוש תשובות: נמצא, "המקור ענה ואין לו את החלק לרכב הזה",
ו"המקור נכשל" — עם הסיבה. השתיים האחרונות נראות דומה ואינן דומות:
רק אחת מהן אומרת "נסה שוב". השער עצמו משנה בהתאם את השאלה — "לנסות
ב-TecDoc?" במקום "להמשיך ל-TecDoc?" — כי זו כבר סיבה אחרת ללחוץ.

`diagram_url` הוא שדה נפרד מ-`image_url` ולא אותו שדה. תצלום מוצר הוא
ממוזערת ליד השורה, ותרשים פיצוץ הוא מה שמסתכלים עליו — כששניהם נדחסו
לאותו שדה, התרשים הוצג ב-64 פיקסלים, וסכמה עם מספרי חלקים בגודל הזה
היא כתם. הוא נשמר על ה-`Part`, ולכן גם חיפוש שנענה מהקטלוג המקומי
מציג אותו.

**כתובות מהמודל מסוננות לפי סכימה.** `source_url` ו-`image_url` הגיעו
מדף של מישהו אחר: אתר קטלוג חיצוני שהמודל קרא. הן נכתבות ל-`href`
ול-`src` במסך, ולכן `parts_discovery.safe_url` מעביר `http`/`https`
בלבד — `javascript:` ב-`href` הוא הרצת קוד במקור של האפליקציה בלחיצה
אחת, עם הסשן של מי שלחץ. הסינון יושב גם ב-`_result_row`, כי הרשימה
**הלא מאומתת** נבנית מהשורה הגולמית ואינה עוברת ב-`validate` — והיא
דווקא זו שאין לסמוך עליה.

**ההתאמה מתרחבת עם כל שנת דגם שנשלפת.** השליפה יודעת שנה מדויקת,
ולכן קורולה 2015 נכנסת לקטלוג כהתאמה `2015-2015` — נכון לרכב שנשאל,
וצר מדי לדגם. כשאותו דגם נשלף בשנה אחרת, טווח השנים של ההתאמה
הקיימת מתרחב (`2015-2016`) במקום להיווצר התאמה כפולה. בלי זה השליפה
השנייה רצה, עלתה כסף, ולא נשמר ממנה דבר: הבדיקה ל"התאמה קיימת"
השוותה יצרן ודגם בלבד וראתה את זו של 2015. ההבחנה נעצרת במנוע —
מנוע אחר הוא התאמה נפרדת, לא הרחבה של הקיימת.

### תקרות, נעילה ומקור מורשה

תקרת שליפות לארגון ליממה (`LOOKUP_DAILY_LIMIT`) — כל שליפה היא כמה
בקשות רשת וכמה קריאות מודל, ובלי תקרה לחיצה חוזרת היא חשבון פתוח.
`robots.txt` נבדק לפני כל הבאה, יש נשימה בין בקשות לאותו מארח,
וה-User-Agent מזהה את עצמו.

במצב קריאה בלבד (`READ_ONLY=1`, ברירת המחדל בפרודקשן) השליפה **רצה
והתוצאה מוצגת** — רק הכתיבה לקטלוג נדחית. הנעילה נועדה להגן על הקטלוג
מעריכה, לא לכבות את זרימת הזיהוי.

המקורות עומדים מאחורי ממשק אחד (`app/catalog_sources/base.py`).
Laximo ו-TecDoc הם ספקים מורשים, וכשמזינים להם אישורי גישה הם רצים
במסלול ה-API — זה מה שהופך את התמונות ואת הנתונים לכשירים לשימוש
מסחרי. בלי אישורי גישה הם רצים במסלול דפדפן, שכפוף לתנאי השימוש של
האתר. בכל מקרה כל מק"ט שנשלף נושא בהערות שלו את המקור שממנו הגיע, כך
שאפשר לאתר ולהחליף את הכל.

## פריסה ל-Railway

### למה זה לא סתם "לחבר ריפו"

SQLite על הדיסק הרגיל של Railway **נמחק בכל deploy** — כל דיפלוי בונה קונטיינר
חדש עם מערכת קבצים נקייה. לכן פרודקשן דורש Postgres (מומלץ) או ווליום קבוע.

### שלבים

1. **צור פרויקט** ב-Railway וחבר אליו את הריפו הזה.
2. **הוסף שירות Postgres** לאותו פרויקט (`+ New → Database → PostgreSQL`).
   Railway מזריק `DATABASE_URL` אוטומטית, והאפליקציה מתרגמת אותו לבד
   לסכמה ש-SQLAlchemy 2 דורש (`postgresql+psycopg://`).
3. **הגדר `SECRET_KEY`** במשתני הסביבה של השירות:
   ```bash
   python -c "import secrets; print(secrets.token_hex(32))"
   ```
   האפליקציה **מסרבת לעלות** על Railway בלי ערך אמיתי — `SECRET_KEY` חותם את
   קוקי הסשן, וערך ברירת המחדל גלוי לכל מי שרואה את הריפו.
4. **לטעינת הקטלוג:** הגדר `IMPORT_PARTS_CSV=data/parts_catalog.csv`. הטעינה
   בטוחה להרצה חוזרת — מק"ט קיים מתעדכן ולא משוכפל.
5. **Generate Domain** בהגדרות השירות — וזהו.

### מה קורה בכל דיפלוי

```
preDeployCommand:  python scripts/init_db.py     ← יוצר טבלאות חסרות, זורע אם ריק
startCommand:      gunicorn --config gunicorn.conf.py "app:create_app()"
healthcheckPath:   /healthz                      ← בודק גם חיבור לבסיס הנתונים
```

`init_db.py` רץ **פעם אחת** לפני שה-workers עולים, ולכן שני workers לא
מתנגשים ביצירת הטבלאות. הוא בטוח להרצה חוזרת.

> **אל תוסיף שורת `release:` ל-`Procfile`.**
> Nixpacks הופך אותה ל**שלב בנייה** בתוך ה-Dockerfile, ו-Railway לא מזריק את
> משתני השירות לבנייה — כך שכל פקודה שם תרוץ בלי `DATABASE_URL` ובלי
> `SECRET_KEY` ותפיל את הבילד. הכנת בסיס הנתונים שייכת ל-`preDeployCommand`
> ב-`railway.json`, שרץ בזמן פריסה עם כל המשתנים.

#### הדפדפן בפריסה

`requirements.txt` מתקין את ספריית Playwright, אבל **לא את Chromium**.
בלי הורדה מפורשת השליפה החיה תעלה כבויה, והמסך יגיד את זה. הדפדפן שייך
לשלב **הבנייה** ולא ל-`preDeployCommand`: הוא כ-400MB שצריכים להיכנס
לתמונה פעם אחת, לא להיות מורדים מחדש בכל דיפלוי.

ב-Railway מוסיפים לשירות **Build Command**:

```
pip install -r requirements.txt && playwright install --with-deps chromium
```

`--with-deps` מתקין גם את ספריות המערכת ש-Chromium דורש, וזה החלק
שנוטה להיחסר בתמונה נקייה. אם הבנייה מוגבלת בהרשאות ו-`--with-deps`
נכשל, אפשר להוריד רק את הדפדפן (`playwright install chromium`) ולהוסיף
את הספריות דרך `nixpacks.toml`.

מי שמעדיף להשאיר את התמונה קלה מכבה את המסלול ב-`CATALOG_BROWSER=0`,
והשליפה החיה פשוט לא מוצעת.

### חלופה בלי Postgres

מצרפים Volume, ממפים ל-`/data`, ומגדירים `DATA_DIR=/data`. פשוט יותר,
אבל מוגבל למכונה אחת — בלי scaling אופקי.

### משתני סביבה

| משתנה | חובה | תפקיד |
|---|---|---|
| `SECRET_KEY` | ✅ בפרודקשן | חתימת קוקי הסשן |
| `DATABASE_URL` | מוזרק ע"י Railway | חיבור ל-Postgres |
| `DATA_DIR` | חלופה | נתיב לווליום עבור SQLite |
| `SUPERADMIN_EMAILS` | לגישת ניהול | כתובות בעלות הרשאת-על, מופרדות בפסיק |
| `IMPORT_PARTS_CSV` | לא | נתיב CSV לטעינת הקטלוג בכל דיפלוי |
| `ANTHROPIC_API_KEY` | לא | מפעיל זיהוי חלק מתמונה |
| `WEB_CONCURRENCY` | לא | מספר workers (ברירת מחדל 2) |
| `ACTIVITY_LOG_ENABLED` | לא | `0` מכבה את כתיבת לוג השימוש |
| `ACTIVITY_LOG_RETENTION_DAYS` | לא | כמה ימים לשמור אירועים (ברירת מחדל 90) |
| `DISPLAY_TIMEZONE` | לא | אזור הזמן להצגה (ברירת מחדל `Asia/Jerusalem`) |

הרשימה המלאה ב-`.env.example`.

## בדיקות

```bash
python -m pytest tests/ -q
```

מכסות את זיהוי החלקים, איתור הרכב, הצלבת רכב×סוג-חלק, חיפוש לפי מק"ט מקביל,
מחזור ייבוא/ייצוא CSV וחישובי מע"מ ורווחיות.

**ומול Postgres.** ברירת המחדל היא SQLite בזיכרון — מהיר ובלי שרת — אבל
פרודקשן רץ על Postgres, ו-SQLite סלחן במקומות שהוא אינו. שאילתה שעברה
כאן ונפלה שם כבר קרתה, ולכן אותה חבילת בדיקות יודעת לרוץ על שניהם:

```bash
createdb makat_test
TEST_DATABASE_URL=postgresql+psycopg://postgres@127.0.0.1:5432/makat_test \
    python -m pytest tests/ -q
```

שני הבדלים שכבר תפסנו כך, ושתי בדיקות שומרות עליהם גם בלי שרת Postgres:

- **`GROUP BY` מושווה לפי טקסט.** ביטוי שהרווח והמקף שלו נשלחים
  כפרמטרים מקבל מספרים שונים ב-SELECT וב-GROUP BY (`$1` מול `$9`),
  ו-Postgres טוען שהעמודה אינה מקובצת. הערכים נכתבים היום לתוך ה-SQL.
- **NULL ממוין ראשון ב-SQLite ואחרון ב-Postgres.** ספירה של מק"ט בלי
  התאמות מחזירה NULL, והתא מציג 0 — כך שאותה לחיצה על כותרת הייתה
  נותנת שתי תשובות שונות. הספירות עטופות ב-`coalesce`.
